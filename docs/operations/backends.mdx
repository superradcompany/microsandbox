SDK resource shortcuts use the local runtime. Select a `RemoteContext` for [microsandbox cloud](/cloud/overview) or another compatible remote API, and a `LocalContext` for a custom local destination. The CLI resolves its own environment and profile selection.

## CLI environment

The `MSB_BACKEND` environment variable selects a backend for a single command or shell, unless an administrator has set a managed active profile:

<CodeGroup>
```bash Shell
MSB_BACKEND=local msb run python -- python -V
MSB_BACKEND=cloud MSB_API_KEY="msb_..." msb ls
```
</CodeGroup>

Cloud selection and credentials are separate. `MSB_API_KEY` does not select cloud by itself. `MSB_API_URL` only overrides the cloud endpoint and does not select cloud either.

## SDK contexts

Keep ordinary local workflows simple: `Sandbox::builder`, `Sandbox.builder`, `Sandbox.create`, and `CreateSandbox` use the default local destination. `MSB_BACKEND`, `MSB_PROFILE`, and `active_profile` do not redirect these shortcuts.

Choose an explicit context when a workflow needs a remote API or a different local home. Contexts, collections, builders, and returned resources retain their destination. Creating another context never changes existing operations.

<CodeGroup>
```typescript TypeScript
import { LocalContext, RemoteContext, Sandbox } from "microsandbox";

const remote = new RemoteContext({ apiKey: process.env.MSB_API_KEY! });
const sb = await remote.sandboxes.builder("task").image("python").create();
const sameDestination = await Sandbox.ctx(remote).get("task");
const local = LocalContext.builder().home("/srv/microsandbox").build();
```

```rust Rust
use microsandbox::{Context, LocalContext, RemoteContext, Sandbox};

let remote = RemoteContext::new(std::env::var("MSB_API_KEY")?)?;
let sb = remote.sandboxes().builder("task").image("python").create().await?;
let same_destination = Sandbox::ctx(&remote).get("task").await?;
let local = LocalContext::builder().home("/srv/microsandbox").build()?;
```

```python Python
import os
from microsandbox import LocalContext, RemoteContext, Sandbox

remote = RemoteContext(api_key=os.environ["MSB_API_KEY"])
sb = await remote.sandboxes.create("task", image="python")
same_destination = await Sandbox.ctx(remote).get("task")
local = LocalContext(home="/srv/microsandbox")
```

```go Go
remote, err := microsandbox.NewRemoteContext(os.Getenv("MSB_API_KEY"))
if err != nil { return err }
sb, err := remote.Sandboxes().Create(ctx, "task", microsandbox.WithImage("python"))
if err != nil { return err }
sameDestination, err := microsandbox.SandboxCtx(remote).Get(ctx, "task")
if err != nil { return err }
local, err := microsandbox.NewLocalContext(microsandbox.LocalOptions{Home: "/srv/microsandbox"})
if err != nil { return err }
```

```ruby Ruby
require "microsandbox"

remote = Microsandbox::RemoteContext.new(api_key: ENV.fetch("MSB_API_KEY"))
sb = remote.sandboxes.builder("task").image("python").create
same_destination = Microsandbox::Sandbox.ctx(remote).get("task")
local = Microsandbox::LocalContext.new(home: "/srv/microsandbox")
```
</CodeGroup>

TypeScript and Python expose `sandboxes`, `volumes`, and `snapshots` as readonly properties. Rust and Go use methods; Ruby uses ordinary no-argument methods. `Volume.ctx` and `Snapshot.ctx` select the equivalent collections, with Rust's `::ctx(&context)` and Go's `VolumeCtx`/`SnapshotCtx` spellings.

Contexts capture user and managed configuration during construction. Invalid files cause an error even when remote credentials are supplied explicitly. Construct a new context to load changed settings. Resource inspection remains live: await `info()`, `status()`, or `config()` to fetch current backend state.

Local context builders are synchronous. They validate and capture configuration immediately; the local catalog opens and migrates on the first operation that requires it.

## Remote endpoints

Key-only construction uses the hosted endpoint, `https://api.microsandbox.dev`. To select another compatible provider, use the explicit-URL factory:

<CodeGroup>
```typescript TypeScript
import { RemoteContext } from "microsandbox";

const remote = RemoteContext.withUrl("https://sandbox.example.com", process.env.MSB_API_KEY!);
```

```rust Rust
use microsandbox::RemoteContext;

let remote = RemoteContext::with_url("https://sandbox.example.com", std::env::var("MSB_API_KEY")?)?;
```

```python Python
import os
from microsandbox import RemoteContext

remote = RemoteContext.with_url("https://sandbox.example.com", os.environ["MSB_API_KEY"])
```

```go Go
remote, err := microsandbox.NewRemoteContextWithURL("https://sandbox.example.com", os.Getenv("MSB_API_KEY"))
if err != nil { return err }
```

```ruby Ruby
require "microsandbox"

remote = Microsandbox::RemoteContext.with_url("https://sandbox.example.com", ENV.fetch("MSB_API_KEY"))
```
</CodeGroup>

An explicitly empty URL is an error. Rust and TypeScript also retain fluent builders for transport settings. TypeScript options and Python/Ruby keyword constructors continue to accept `url`; their explicit-URL factories share the same validation and timeout/user-agent options. Go's selected `NativeProvider` exposes the same `NewRemoteContext(apiKey)` and `NewRemoteContextWithURL(url, apiKey)` methods.

Use `from_env` / `fromEnv` / `RemoteContextFromEnv` to read `MSB_API_KEY` and optional `MSB_API_URL`, or the corresponding named-profile constructor to load a profile. Key-only construction does not read `MSB_API_URL` to choose an endpoint. None of these constructors changes the default-local resource shortcuts.

## Deriving a remote context

Derive a remote context when you need a different endpoint, API key or transport setting while keeping the original available. Omitted settings retain their captured values. Derivation does not reread environment variables, named profiles or configuration files, and it uses the same native provider. Existing collections, builders and resources retain their original context; changing a derived context does not rotate credentials on those objects.

<CodeGroup>
```typescript TypeScript
import { RemoteContext } from "microsandbox";

const remote = RemoteContext.fromEnv();
const other = remote.toBuilder()
  .url("https://other-provider.example")
  .apiKey(process.env.OTHER_API_KEY!)
  .build();
```

```rust Rust
use microsandbox::RemoteContext;

let remote = RemoteContext::from_env()?;
let other = remote.to_builder()
    .url("https://other-provider.example")
    .api_key(std::env::var("OTHER_API_KEY")?)
    .build()?;
```

```python Python
import os
from microsandbox import RemoteContext

remote = RemoteContext.from_env()
other = remote.replace(
    url="https://other-provider.example",
    api_key=os.environ["OTHER_API_KEY"],
)
```

```go Go
import (
    "os"
    m "github.com/superradcompany/microsandbox/sdk/go"
)

remote, err := m.RemoteContextFromEnv()
if err != nil { return err }
other, err := remote.WithOptions(
    m.WithRemoteURL("https://other-provider.example"),
    m.WithRemoteAPIKey(os.Getenv("OTHER_API_KEY")),
)
if err != nil { return err }
```

```ruby Ruby
require "microsandbox"

remote = Microsandbox::RemoteContext.from_env
other = remote.with(
  url: "https://other-provider.example",
  api_key: ENV.fetch("OTHER_API_KEY")
)
```
</CodeGroup>

Rust and TypeScript use their existing fluent builders. Python and Ruby use keyword overrides; `None`/`nil` retain the captured value. Go uses functional options. Python/Ruby accept `request_timeout_ms` and `user_agent`; Go provides `WithRemoteRequestTimeout(time.Duration)` and `WithRemoteUserAgent(string)`. Go durations must be nonnegative and are rounded down to milliseconds. Explicit empty URLs or API keys are rejected. Rust/TypeScript validate on `build()`; the other SDKs validate when deriving. None of these operations contacts the remote service.

In Rust, `clone()` remains a cheap shared clone. `to_builder().build()` constructs an independent context while sharing the existing HTTP transport and its captured proxy/TLS settings. Timeout and user-agent overrides apply to requests from the derived context. A supplied custom client retains its transport settings and connection pool; its timeout and user-agent settings still take precedence over those builder options. The context API key supplies Authorization on every HTTP request, including with a custom client, matching agent connections. A derived context has programmatic provenance and does not carry a resource-specific agent identity binding.

## CLI profiles

Profiles are named backend configurations in `~/.microsandbox/config.json`. Use them when you switch regularly or want a shared default for an environment:

<CodeGroup>
```json JSON
{
  "active_profile": "production",
  "profiles": {
    "production": {
      "kind": "remote",
      "api_key_ref": "env:MSB_API_KEY"
    },
    "local": {
      "kind": "local"
    }
  }
}
```
</CodeGroup>

Profile writers use `kind: "local"` or `kind: "remote"`. Readers also accept legacy `backend` and `cloud` spellings. Older SDKs may reject newly written profiles; update those clients before sharing a rewritten configuration.

`active_profile` sets the CLI default. `MSB_PROFILE=<name>` selects another profile for one command:

<CodeGroup>
```bash Shell
MSB_PROFILE=production msb run python -- python -V
```
</CodeGroup>

Cloud profiles require `api_key_ref`. The optional `url` field defaults to `https://api.microsandbox.dev`; set it only for a development, self-hosted, or on-premises control plane. See the [profiles schema](/configuration#profiles) for every field and credential-reference format.

## Precedence

CLI backend resolution uses this order:

1. Managed `active_profile`, if supplied
2. `MSB_BACKEND=local|cloud`
3. `MSB_PROFILE=<name>`
4. User `active_profile`
5. Local runtime

A managed `active_profile` set to `null` or an empty string clears saved and environment-selected profiles while preserving `MSB_BACKEND`. With no explicit backend, it uses the local fallback. To enforce local execution over `MSB_BACKEND`, select a named managed profile with `kind: local`. Managed profile entries replace same-named user entries. See [Managed deployment](/enterprise/managed-configuration) for deployment and file format. An explicitly constructed SDK backend keeps its identity. Both local and cloud backends apply managed sandbox settings and host-side SSH policy.

Selecting a cloud profile with `MSB_PROFILE` or `active_profile` is explicit cloud intent when that profile has `"kind": "remote"`. `MSB_BACKEND=cloud` without a usable API key or cloud profile returns a configuration error; it never falls back to local execution.

### Permit local, cloud, or both

Set `"allowed_backends": ["local"]`, `["cloud"]`, or `["local", "cloud"]` in user config or managed overrides. The default is both. An empty list is invalid; `null` removes the restriction. Managed values replace user values.

Permission is separate from selection. A cloud-only policy rejects local selection; it does not select cloud for you. Checks apply when standard SDK or CLI backends are constructed, including explicitly supplied backends. Existing backend instances keep their captured settings.

Use `msb context list` to inspect profiles without loading credentials, `msb context use <name>` to save a preference, and `msb context reset` to remove it. See [context commands](/cli/management#msb-context) for precedence and recovery.

## Verify

Use `msb context` to inspect the backend kind, selection source, profile, and cloud API URL without exposing the API key:

<CodeGroup>
```bash Shell
msb context
msb context --format json
```
</CodeGroup>

SDK callers inspect the context retained by a resource: `sandbox.context` in TypeScript and Python, `sandbox.context()` in Rust, `sandbox.Context()` in Go, and `sandbox.context` in Ruby. There is no mutable process-wide SDK destination or ambient scope to inspect.

For global defaults and profile storage, see [Configuration](/operations/configuration). For backend feature differences, see [Cloud compatibility](/cloud/overview#compatibility).
