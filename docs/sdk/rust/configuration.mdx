## GlobalConfigPatch

### load()

```rust
fn load() -> MicrosandboxResult<Self>
```

Read saved user settings while preserving omitted fields and explicit clears. A missing file returns an empty patch. Defaults and managed overrides are applied later.

### save()

```rust
fn save(&self) -> MicrosandboxResult<()>
```

Save the patch without filling in defaults. Omitted fields stay omitted and explicit clears are preserved. Unknown user fields are ignored on load and discarded on save.

## GlobalConfig

Resolved settings after layering. Use [`LocalContext::config()`](#config) to read the effective configuration for a backend.

## LocalContext

### config()

```rust
fn config(&self) -> &GlobalConfig
```

Read the settings retained by this backend. Existing handles keep their configuration when files or process defaults change.

### Runtime paths

Inspect the active config and resolve runtime paths with the same precedence used by sandbox startup:

<Accordion title="Example">

```rust
use microsandbox::{config::config, setup::resolve_runtime};

let cfg = config()?;
let runtime = resolve_runtime(&cfg)?;
let msb = &runtime.msb_path;
let libkrunfw = &runtime.libkrunfw_path;
```

</Accordion>

When your code owns an explicit local backend, prefer the backend-owned config:

<Accordion title="Example">

```rust
use microsandbox::{setup::resolve_runtime, LocalContext};

let backend = LocalContext::builder()
    .home("/tmp/msb-home")
    .build()?;

let cfg = backend.config();
let runtime = resolve_runtime(cfg)?;
```

</Accordion>

`LocalContext` has two plain constructors alongside the builder. `LocalContext::lazy()?` is synchronous and defers opening (and migrating) the local sandbox database until the first operation; it is what backend resolution uses when no backend is set explicitly. `LocalContext::new().await?` opens the database up front, so startup fails fast if the database is unusable. All constructors read, layer, and validate global configuration before returning a backend; only database setup is lazy. Proxy settings are validated after sandbox options and managed overrides are composed, before network use.

`LocalContextBuilder::build()` now returns `Result<LocalContext>`. It replaces `try_build()`, and `LocalContext` no longer implements `Default`; use `LocalContext::lazy()?` instead.

For a long-lived process, construct a new context to pick up configuration changes. Bind subsequent work with `Sandbox::ctx(&context)` or the context’s collections. Existing collections, builders and resources retain their original destination and settings.

## LocalContextBuilder

### config_path()

```rust
fn config_path(self, path: impl Into<PathBuf>) -> Self
```

Read a specific user configuration file without changing `MSB_CONFIG_PATH`. Managed settings still apply. The builder's `home()` selects data storage; it does not select the configuration file. Backend-selection helpers and synchronous constructors remain synchronous.

<Accordion title="Example">

```rust
use microsandbox::LocalContext;

let backend = LocalContext::builder()
    .config_path("/etc/my-app/microsandbox.json")
    .build()?;
```

</Accordion>

### deployment_profile()

```rust
fn deployment_profile(self, profile: DeploymentProfile) -> Self
```

Set the deployment profile for this backend. It takes precedence over the user configuration file and each sandbox's requested profile on create and restart. Managed settings retain precedence. See [deployment profiles](/configuration#deployment_profile) for behavior.

### ssh_inactivity_timeout_secs()

```rust
fn ssh_inactivity_timeout_secs(self, secs: u64) -> Self
```

Override the user-configured SSH inactivity timeout. Zero disables it; managed settings retain precedence. See [SSH settings](/configuration#ssh) for when the value is captured.

## Sandbox configuration patches

Use [`SandboxBuilder::overlay()`](/sdk/rust/sandbox#sandbox-overlay) to override individual settings or explicitly clear an inherited working directory. These choices survive `SandboxBuilder::from(config)` and local database reloads. Without saved caller overrides, `workdir: None` still means omitted.

Edit settings through builder setters, `overlay()`, or sandbox modification APIs; saved overrides can overwrite direct edits to a resolved `SandboxConfig`. See [configuration layering](/configuration#sandbox_defaults) for precedence and backend differences.

## Context

### sandboxes(), volumes(), snapshots()

```rust
fn sandboxes(&self) -> Sandboxes;
fn volumes(&self) -> Volumes;
fn snapshots(&self) -> Snapshots;
```

Choose which connection resource builders use. These accessors perform no backend I/O. Collections and builders keep using that connection even after the original variable goes out of scope. Use the default resource builders for local execution, or choose a context for remote execution or custom local settings.

<Accordion title="Example">
```rust
use microsandbox::{Context, LocalContext, Sandbox};

let context = LocalContext::builder().home("/srv/msb/project-a").build()?;
let direct = Sandbox::ctx(&context).builder("worker-a").image("python");
let collection = context.sandboxes().builder("worker-b").image("python");
drop(context);
let worker_a = direct.create().await?;
let worker_b = collection.create().await?;
```
</Accordion>

### clone_shared()

```rust
fn clone_shared(&self) -> std::sync::Arc<dyn Context>;
```

Clone the context while sharing its connection and settings. `LocalContext` clones share configuration, database initialization and control state. `RemoteContext` clones share their HTTP client and captured configuration. Context binding accepts `&dyn Context`; callers do not need to allocate an `Arc` themselves.

### Resource and builder context()

```rust
fn context(&self) -> &dyn Context;
```

`Sandbox`, `Volume`, `Snapshot` and their builders expose their connection through this synchronous accessor. It returns the existing connection without allocating or contacting the backend. Use it to select another collection on the same destination.

## RemoteContext

### new() / with_url()

```rust
fn new(api_key: impl Into<String>) -> MicrosandboxResult<Self>;
fn with_url(url: impl Into<String>, api_key: impl Into<String>) -> MicrosandboxResult<Self>;
```

`new(api_key)` uses `MSB_API_URL` or the hosted endpoint. Use `with_url(url, api_key)` to specify both.

### builder()

```rust
fn builder() -> RemoteContextBuilder;
```

Configure a remote endpoint, credentials and transport options. The builder’s synchronous `build()` validates and captures its settings. Resource requests happen through its collections or `Resource::ctx(&context)`.

<Accordion title="Example">
```rust
use microsandbox::{Context, RemoteContext};

let context = RemoteContext::builder()
    .url("https://api.example.com")
    .api_key(std::env::var("MSB_API_KEY")?)
    .build()?;
let sandbox = context.sandboxes().builder("worker").image("python").create().await?;
```
</Accordion>

### to_builder()

```rust
fn to_builder(&self) -> RemoteContextBuilder;
```

Return a builder initialized from captured endpoint, credentials, compute type, transport options and configuration. Building creates an independent context without rereading profiles, environment or configuration files. Existing resources retain their original context. A supplied custom HTTP client keeps its transport settings; the context API key controls Authorization. See [derivation examples](/cloud/connect#deriving-a-remote-context).

<Accordion title="Example">
```rust
let other = remote.to_builder().api_key(other_key).build()?;
```
</Accordion>

## RemoteContextBuilder

### compute_type()

```rust
fn compute_type(self, compute_type: ComputeType) -> Self
```

Choose `Standard` or `Shared` for new sandboxes and snapshot restores. Omission uses the server default. Existing sandboxes keep their type. See [compute types](/cloud/pricing#choose-a-compute-type).

<Accordion title="Example">
```rust
use microsandbox::{ComputeType, RemoteContext};

let remote = RemoteContext::builder()
    .compute_type(ComputeType::Shared)
    .build()?;
```
</Accordion>
