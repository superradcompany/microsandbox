Coding agents routinely run package installers, build scripts, tests, and generated shell commands. This recipe gives an MCP-compatible agent a disposable microVM, keeps the repository clone away from your host filesystem, and brings back only a patch you review.

The example uses Claude Code, but the workflow works with any client supported by the [microsandbox MCP server](/getting-started/agents#mcp-server).

## Connect the MCP server

```bash
claude mcp add --transport stdio microsandbox -- npx -y microsandbox-mcp
```

Start your agent from an empty working directory or a directory you are comfortable allowing as an export destination. By default, the MCP server allows host file operations only inside its current working directory.

For a narrower export boundary, set the allowlist explicitly before starting your client:

```bash
export MICROSANDBOX_MCP_HOST_PATHS="$PWD/agent-output"
mkdir -p "$MICROSANDBOX_MCP_HOST_PATHS"
```

## Ask the agent to work in a microVM

Give the agent a concrete repository, task, and test command. This prompt keeps all repository access inside the sandbox and asks for review before anything is copied to the host:

```text
Use only the microsandbox MCP tools for shell commands and filesystem operations in this task.

1. Check the microsandbox runtime and install it if it is missing.
2. Create a sandbox named coding-task from an Ubuntu image with 2 CPUs and 4 GiB of memory.
3. Inside the sandbox, clone https://github.com/OWNER/REPOSITORY.git to /workspace.
4. Make this change: <describe the task precisely>.
5. Run these checks from /workspace: <exact test and lint commands>.
6. Run `git status --short`, then `git add -N .` so new files appear without staging their contents. Show me the test results, `git diff --stat`, and `git diff`.
7. Do not mount a host directory, copy files to the host, push commits, or remove the sandbox until I approve the diff.
```

The agent can now inspect files, edit code, install dependencies, and run tests without giving guest processes access to your host checkout. The sandbox remains available while you review the result.

<Tip>
  Public repositories need no credentials. For private repositories, use microsandbox [secret injection](/sandboxes/secrets) and an allowlisted Git host instead of placing a token in the clone URL, environment, prompt, or guest filesystem.
</Tip>

## Review and export a patch

After the agent shows the diff, ask it to create and export one patch:

```text
The diff is approved. In the coding-task sandbox, run `git add -N .` and write `git diff --binary` to /tmp/coding-task.patch. Copy only that file to /absolute/path/to/agent-output/coding-task.patch, then stop and remove the sandbox.
```

Check the patch before applying it to your real checkout:

```bash
git apply --stat ./agent-output/coding-task.patch
git apply --check ./agent-output/coding-task.patch
git apply ./agent-output/coding-task.patch
```

This separates three trust decisions: the agent may execute freely inside the VM, you review the proposed change, and only an approved patch crosses back to the host.

## Tighten the workflow

- Pin the base image by digest when reproducibility matters.
- Set explicit command timeouts and output caps in the MCP server configuration.
- Use a deny-by-default [network policy](/networking/overview) and allow only the source host and package registries the task needs.
- Keep `MICROSANDBOX_MCP_HOST_PATHS` scoped to a dedicated output directory. Do not set `MICROSANDBOX_MCP_HOST_PATH_POLICY=unrestricted` for agent workflows.
- Inspect `git status --short` as well as the textual diff. The recipe uses `git add -N .` so untracked files appear in the diff without staging their contents.
- Use a fresh sandbox per untrusted repository or unrelated task, then remove it after exporting the reviewed result.

If you want the agent to operate microsandbox through learned CLI patterns instead of MCP tools, install the [Agent Skill](/getting-started/agents#agent-skills).
