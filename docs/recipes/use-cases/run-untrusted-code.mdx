Use this pattern for a code playground, grading service, plugin system, data-analysis app, or any feature that executes code you did not write. Each submission gets a fresh microVM, and the guest is stopped and removed when the run finishes.

This example uses the TypeScript SDK and Python, but the same lifecycle works with any OCI image and command.

## Quick CLI smoke test

Before building a service, verify the core isolation controls from the terminal:

```sh
msb run --name restricted-python --replace \
  --cpus 1 --memory 256M \
  --no-net --security restricted \
  --rlimit nproc=64 --rlimit nofile=128 \
  --max-duration 30s \
  python:3.13-slim -- python -c '
import socket
from pathlib import Path

Path("/tmp/worked").write_text("sandboxed")
try:
    socket.create_connection(("example.com", 443), timeout=2)
    raise SystemExit("network unexpectedly reachable")
except OSError as error:
    print("network blocked:", type(error).__name__)

print("filesystem ok:", Path("/tmp/worked").read_text())
  '
```

The command should print `network blocked: gaierror` followed by `filesystem ok: sandboxed`, then stop. Remove its persisted record with:

```sh
msb rm restricted-python
```

## Create a bounded runner

```typescript run-python.ts
import { randomUUID } from "node:crypto";
import { MiB, Sandbox } from "microsandbox";

const MAX_SOURCE_BYTES = 64 * 1024;

export type RunResult = {
  exitCode: number;
  stdout: string;
  stderr: string;
};

export async function runPython(source: string): Promise<RunResult> {
  if (Buffer.byteLength(source, "utf8") > MAX_SOURCE_BYTES) {
    throw new Error("source exceeds the 64 KiB limit");
  }

  const name = `submission-${randomUUID()}`;
  const sandbox = await Sandbox.builder(name)
    .image("python")
    .cpus(1)
    .memory(MiB(512))
    .disableNetwork()
    .patch((patch) => patch.mkdir("/workspace", { mode: 0o755 }))
    .workdir("/workspace")
    .create();

  try {
    await sandbox.fs().write("/workspace/main.py", source);

    const output = await sandbox.execWith("python", (exec) =>
      exec
        .args(["-I", "main.py"])
        .timeout(5_000)
        .rlimit("cpu", 5)
        .rlimit("nproc", 64)
        .rlimit("nofile", 128)
        .rlimit("fsize", 10 * 1024 * 1024),
    );

    return {
      exitCode: output.code,
      stdout: output.stdout(),
      stderr: output.stderr(),
    };
  } finally {
    await sandbox.stop();
    await Sandbox.remove(name);
  }
}
```

Call it from an API handler or worker:

```typescript
const result = await runPython("print(sum(range(10)))");
console.log(result);
// { exitCode: 0, stdout: "45\n", stderr: "" }
```

## What the limits do

| Control | Protection |
|---|---|
| Fresh microVM | Keeps guest processes and the guest filesystem outside the host process |
| `cpus(1)` and `memory(MiB(512))` | Bounds the VM's compute and memory allocation |
| `disableNetwork()` | Blocks guest network access, so submitted code cannot make network requests |
| `timeout(5_000)` and `rlimit("cpu", 5)` | Stops wall-clock hangs and CPU-bound loops |
| `nproc`, `nofile`, and `fsize` | Limits process creation, open file descriptors, and file size |
| `finally` cleanup | Stops the VM and removes its persisted sandbox record after every run |

<Warning>
  `execWith()` collects stdout and stderr in host memory. Enforce an application-level output limit, or use [`execStreamWith()`](/sdk/typescript/execution#sandbox-execstreamwith) and stop reading after your cap, before accepting arbitrary public submissions.
</Warning>

## Production checklist

- Put a concurrency limit in front of the runner so submissions cannot exhaust host CPU, memory, or disk by creating too many VMs at once.
- Validate source and request sizes before booting a sandbox.
- Use a purpose-built image with only the runtime and packages submissions need.
- Keep networking disabled unless the workload requires it. If it does, use a deny-by-default [network policy](/networking/overview).
- Do not bind-mount host directories or pass host credentials into a sandbox that runs untrusted code.
- Record exit status, duration, and resource metrics for abuse detection, but avoid logging submitted source when it may contain private data.

For longer-running or interactive workloads, see [Command execution](/sandboxes/commands). For controlled API credentials that never enter the VM, see [Secrets](/sandboxes/secrets).
