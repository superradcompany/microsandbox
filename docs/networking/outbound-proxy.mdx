Configure one HTTP CONNECT, SOCKS4, or SOCKS5 proxy for outbound sandbox traffic. The guest connects to its normal destination; microsandbox routes eligible traffic through the proxy on the host.

Set `sandbox_defaults.outbound_proxy` in [global configuration](/configuration#sandbox_defaults) for a shared default. Administrators can enforce or clear it through [managed configuration](/enterprise/corporate-networking#route-sandbox-traffic), which takes precedence over per-sandbox CLI and SDK options.

## Supported proxies

| Proxy | Authentication | Traffic | Availability |
|-------|----------------|---------|--------------|
| HTTP CONNECT | None | TCP | SDKs and CLI |
| HTTP CONNECT with proxy-side DNS | None | HTTP and HTTPS clients using proxy environment variables | SDKs and CLI |
| SOCKS4 | None | TCP | SDKs and CLI |
| SOCKS4 | Optional user ID | TCP | SDKs and CLI |
| SOCKS5 | None | TCP and non-DNS UDP | SDKs and CLI |
| SOCKS5 | Optional username and password | TCP and non-DNS UDP | SDKs and CLI |

You can configure only one proxy for a sandbox. A SOCKS4 user ID identifies the caller; it is not a password.

## Configure a proxy

<CodeGroup>
```typescript TypeScript
import { Sandbox } from "microsandbox";

await using sb = await Sandbox.builder("proxied")
  .image("python")
  .proxy((p) => p.socks5("127.0.0.1:1080"))
  .create();
```

```rust Rust
use microsandbox::Sandbox;

let sb = Sandbox::builder("proxied")
    .image("python")
    .proxy(|p| p.socks5("127.0.0.1:1080"))
    .create()
    .await?;
```

```python Python
from microsandbox import OutboundProxy, Sandbox

sb = await Sandbox.create(
    "proxied",
    image="python",
    proxy=OutboundProxy.socks5("127.0.0.1:1080"),
)
```

```go Go
sb, err := m.CreateSandbox(ctx, "proxied",
    m.WithImage("python"),
    m.WithProxy(m.SOCKS5Proxy("127.0.0.1:1080")),
)
```

```bash CLI
# Choose one:
msb create python --name proxied --proxy http://127.0.0.1:3128
msb create python --name proxied --proxy socks4://127.0.0.1:1080
msb create python --name proxied --proxy socks5://127.0.0.1:1080
```
</CodeGroup>

SDK addresses use `IP:port`. The `msb run` and `msb create` commands accept `--proxy http://IP:port`, `http+proxy-dns://IP:port`, `socks4://IP:port`, or `socks5://IP:port`. Proxy URIs reject user information, paths, query parameters, and fragments; SOCKS authentication uses separate CLI flags.

## HTTP CONNECT

HTTP CONNECT opens a TCP tunnel through an HTTP proxy. It does not support proxy authentication or UDP. microsandbox resolves and checks the destination using its normal DNS and egress policy before sending the destination IP and port in the CONNECT request. The proxy address itself must be an IP address with a port.

The selected `msb` runtime must support HTTP CONNECT. When using an older runtime, the SDK requests an upgrade before creating or replacing a sandbox.

<CodeGroup>
```typescript TypeScript
.proxy((p) => p.httpConnect("127.0.0.1:3128"))
```

```rust Rust
.proxy(|p| p.http_connect("127.0.0.1:3128"))
```

```python Python
proxy=OutboundProxy.http_connect("127.0.0.1:3128")
```

```go Go
m.WithProxy(m.HTTPConnectProxy("127.0.0.1:3128"))
```

```bash CLI
msb run alpine --proxy http://127.0.0.1:3128
```
</CodeGroup>

## Proxy-side DNS resolution

Enable proxy-side DNS on an HTTP CONNECT proxy when HTTP clients must use the upstream proxy's resolver. The sandbox starts a local HTTP forward proxy and supplies it through `HTTP_PROXY`, `HTTPS_PROXY`, and their lowercase equivalents. The local proxy checks each requested hostname against the sandbox and platform domain policy, then forwards HTTP requests in absolute form with a `Host` header matching the checked URL authority; HTTPS tunnels use `CONNECT hostname:port`. The guest does not need to send network traffic directly to the upstream proxy.

HTTP Upgrade requests, including WebSocket handshakes, preserve their upgrade headers. The local proxy starts a bidirectional tunnel through the policy-checked upstream connection only after the upstream accepts the upgrade with `101 Switching Protocols`. A rejected upgrade returns the upstream response and closes the connection. Refusal bodies use HTTP response framing, including connection-close framing for a final non-chunked transfer coding such as `gzip`.

When any secrets are configured, the local HTTP proxy rejects Upgrade requests with `403 Forbidden` before connecting upstream. Upgraded payloads, such as masked WebSocket frames, cannot be checked reliably by the HTTP secret handler. The response explains this restriction; ordinary HTTP secret substitution continues to work.

With secrets configured, CONNECT requires TLS interception. Tunnels with interception disabled, on ports outside the interception list, or to a hostname configured for TLS bypass receive an explanatory `403 Forbidden` before connecting upstream, including secret-allowed hosts. If an IP-literal CONNECT selects a TLS bypass through its SNI, the tunnel closes before forwarding the TLS payload. Intercepted CONNECT tunnels continue through the existing TLS secret handler.

The local proxy handles one ordinary HTTP request per TCP connection. It detects additional request data after the request body, including chunked bodies and requests split across network reads. If detected before the response starts, the proxy returns `400 Bad Request`; if the response has already started, it closes the connection. Use a new connection for another request.

This mode is unavailable with the multi-tenant deployment profile, which disables user-configured outbound proxies.

```typescript
.proxy((p) => p.httpConnect("127.0.0.1:3128").resolveDnsViaProxy())
```

```rust
.proxy(|p| p.http_connect("127.0.0.1:3128").resolve_dns_via_proxy())
```

```python
proxy=OutboundProxy.http_connect("127.0.0.1:3128", resolve_dns_via_proxy=True)
```

```go
m.WithProxy(m.HTTPConnectProxyWithProxyDNS("127.0.0.1:3128"))
```

```bash
msb run alpine --proxy http+proxy-dns://127.0.0.1:3128
```

Domain rules, ports, protocols, and default egress policy still apply. Because the upstream proxy resolves the hostname, microsandbox cannot apply CIDR or destination-group rules, including `Public`, to that DNS result. A policy that allows only an IP group does not allow proxy-resolved hostnames; use hostname rules or an applicable `Any` rule. The upstream proxy's DNS answer and destination selection are trusted, so the DNS blocklist and DNS rebinding checks do not see these requests. IP literals still receive normal address-based policy checks; TLS interception also applies hostname deny rules to their SNI.

TLS interception and secret injection continue to work for HTTPS clients that use the injected proxy and connect with a hostname matching the TLS SNI. Raw TCP and UDP packets do not use this local HTTP proxy and retain the existing direct network-policy path. Raw DNS continues through the existing DNS forwarder. The proxy variables are baseline defaults; workload-supplied proxy variables can override them, and HTTP requests that bypass the local proxy do not receive its hostname checks.

The selected `msb` runtime must advertise HTTP CONNECT proxy-side DNS support. Older runtimes are refused before sandbox creation or replacement.

## SOCKS4 user ID

Add an optional user ID through an SDK or `--socks4-user-id` in the CLI.

<CodeGroup>
```typescript TypeScript
.proxy((p) => p.socks4("127.0.0.1:1080").userId("sandbox"))
```

```rust Rust
.proxy(|p| p.socks4("127.0.0.1:1080").user_id("sandbox"))
```

```python Python
proxy=OutboundProxy.socks4("127.0.0.1:1080", user_id="sandbox")
```

```go Go
m.WithProxy(m.SOCKS4Proxy(
    "127.0.0.1:1080",
    m.SOCKS4ProxyOptions{UserID: "sandbox"},
))
```

```bash CLI
msb run alpine \
  --proxy socks4://127.0.0.1:1080 \
  --socks4-user-id sandbox
```
</CodeGroup>

The user ID must contain 1–255 bytes and cannot contain a null byte. Omit it to use SOCKS4 without a user ID.

## SOCKS5 credentials

SOCKS5 supports optional username/password authentication. Passwords are loaded from a host environment variable rather than placed directly in configuration.

<CodeGroup>
```typescript TypeScript
.proxy((proxy) =>
  proxy.socks5("127.0.0.1:1080").credentials(
    "sandbox",
    SecretSource.env("SOCKS5_PASSWORD"),
  ),
)
```

```rust Rust
.proxy(|proxy| {
    proxy.socks5("127.0.0.1:1080").credentials(
        "sandbox",
        SecretSource::env("SOCKS5_PASSWORD"),
    )
})
```

```python Python
proxy = OutboundProxy.socks5("127.0.0.1:1080").credentials(
    "sandbox",
    SecretSource.env("SOCKS5_PASSWORD"),
)
```

```go Go
proxy := m.SOCKS5Proxy("127.0.0.1:1080").Credentials(
    "sandbox",
    m.SecretSourceEnv("SOCKS5_PASSWORD"),
)
m.WithProxy(proxy)
```

```bash CLI
msb run alpine \
  --proxy socks5://127.0.0.1:1080 \
  --socks5-username sandbox \
  --socks5-password-env SOCKS5_PASSWORD
```
</CodeGroup>

- **Password source:** Set the password in a host environment variable, the only supported source. Configuration stores only the variable name, such as `SOCKS5_PASSWORD`, never the password.
- **When changes apply:** The password is read when the sandbox starts. Restart the sandbox after changing it.
- **Requirements:** The username and password must each contain 1–255 bytes. Startup fails if the password variable is missing, empty, or invalid.

<Warning>
  SOCKS5 authentication does not encrypt credentials in transit. Use a trusted local or private proxy, or encrypt the connection separately.
</Warning>

## Behavior and limits

- For ordinary HTTP CONNECT, network policy is evaluated against the resolved destination before the proxy connection is opened. With proxy-side DNS, policy is evaluated against the hostname because the upstream proxy's resolved IP is unavailable.
- Ordinary HTTP CONNECT and SOCKS4 support TCP only. Non-DNS UDP is blocked while either is configured; SOCKS4 also cannot reach IPv6 destinations. Proxy-side DNS mode leaves raw UDP on the normal policy path.
- SOCKS5 uses `CONNECT` for TCP and `UDP ASSOCIATE` for non-DNS UDP.
- Raw DNS uses microsandbox's DNS forwarder instead of the configured proxy. This includes plain DNS, DNS-over-TCP, and DNS-over-TLS. Proxy-side DNS applies only to HTTP clients using `HTTP_PROXY` or `HTTPS_PROXY`.
- Connections to `host.microsandbox.internal` bypass the proxy and continue to target the microsandbox host.
- Ordinary proxy-routed TCP connections open one upstream connection each. Proxy-side DNS uses one upstream connection per plain HTTP request or HTTPS tunnel. Each UDP flow opens its own SOCKS5 control connection and UDP association.
- TLS interception and secret injection continue to work as configured.
