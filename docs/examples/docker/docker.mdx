<Tooltip tip="The container runs the local microsandbox backend and needs hardware virtualization from its Docker host. It is not a microsandbox cloud workflow."><span className="msb-badge-local">Local-only <Icon icon="circle-info" size={11} /></span></Tooltip>

The published image packages `msb` and `libkrunfw` in a Linux container. It does not replace the hypervisor: Docker must still expose `/dev/kvm` so microsandbox can start a microVM inside the container.

```text
Linux          host → Docker container → microVM
macOS/Windows  host → Docker Desktop VM → container → microVM
```

For production hosts, [installing microsandbox directly](/getting-started/quickstart) avoids this extra virtualization layer. The container image is useful when an existing deployment system requires an OCI image.

## Requirements

| Docker host | Requirement |
| --- | --- |
| <Icon icon="linux" size={16} /> **Linux** | Docker Engine with a readable and writable `/dev/kvm` device. |
| <Icon icon="apple" size={16} /> **macOS** | Docker Desktop with nested virtualization and `/dev/kvm` exposed through its Linux VM. |
| <Icon icon="windows" size={16} /> **Windows** | Docker Desktop with nested virtualization and `/dev/kvm` exposed through its WSL 2 or Hyper-V Linux environment. |

The image supports `linux/amd64` and `linux/arm64`. Architecture compatibility does not imply virtualization support; `/dev/kvm` is the authoritative check. Docker Desktop runs Linux containers in a VM on [macOS](https://docs.docker.com/desktop/features/vmm/) and through a Linux environment such as [WSL 2 on Windows](https://docs.docker.com/desktop/features/wsl/). Installing Docker Desktop does not guarantee that nested KVM reaches containers, so use the preflight below. If it fails, use the [native installation](/getting-started/quickstart) or microsandbox cloud.

## Verify the Docker host

Pull the image, then run `msb doctor` inside it before starting a sandbox:

```bash
docker pull ghcr.io/superradcompany/microsandbox:latest

docker run --rm --device /dev/kvm \
  ghcr.io/superradcompany/microsandbox:latest \
  doctor
```

A compatible Docker host reports both checks as successful:

```text
✓ KVM device   /dev/kvm
✓ KVM access   read/write
```

If Docker rejects the device mapping or `msb doctor` reports that `/dev/kvm` is missing, nested virtualization is not reaching the container. Adding `--privileged` cannot create a KVM device that the Docker host does not have.

## Open an interactive sandbox

Run Alpine and attach your terminal to its shell:

```bash
docker run --rm -it \
  --device /dev/kvm \
  ghcr.io/superradcompany/microsandbox:latest \
  run alpine --name my-sandbox --replace
```

- `--rm` removes the outer container when it exits.
- `-it` carries your terminal through Docker and `msb` to the sandbox. Without it, the sandbox can be running with no usable prompt.
- `--device /dev/kvm` grants the specific hardware interface microsandbox needs. The container does not require Docker's blanket `--privileged` mode.

At the Alpine prompt, verify the guest and exit:

```sh
uname -a
exit
```

## Run one command

For automation, pass a command instead of allocating a terminal:

```bash
docker run --rm --device /dev/kvm \
  ghcr.io/superradcompany/microsandbox:latest \
  run alpine --name my-sandbox --replace -- \
  echo "hello from a microVM"
```

The command's output and exit code pass through both layers to the host.

## Persist images and sandboxes

Without a volume, the outer container owns the microsandbox image cache and database. `--rm` deletes them with the container, so the next run downloads Alpine again. Mount a Docker volume when repeated runs should reuse that state:

```bash
docker volume create microsandbox-data

docker run --rm -it \
  --device /dev/kvm \
  --volume microsandbox-data:/root/.microsandbox \
  ghcr.io/superradcompany/microsandbox:latest \
  run alpine --name my-sandbox --replace
```

The Docker volume preserves pulled images, stopped sandboxes, snapshots, and the microsandbox database. Remove it only when that state is no longer needed:

```bash
docker volume rm microsandbox-data
```

## Troubleshooting

<AccordionGroup>
  <Accordion title="The process exits with SIGABRT before the agent starts">
    Run the `msb doctor` preflight above. An early abort while entering the VM commonly means the outer Linux environment did not provide usable KVM access.
  </Accordion>
  <Accordion title="The command keeps running but shows no prompt">
    Check that the Docker command includes `-it`. From another terminal, `docker ps` may show that the outer container is running even though its standard input and terminal were not attached.
  </Accordion>
  <Accordion title="The guest image downloads on every run">
    Mount `microsandbox-data` at `/root/.microsandbox`. An ephemeral outer container otherwise starts with an empty microsandbox cache.
  </Accordion>
</AccordionGroup>
