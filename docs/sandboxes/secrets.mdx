Secrets keep credentials on the host while giving sandboxed code a placeholder to use.

When you bind a secret to an environment variable, microsandbox puts a placeholder in the guest instead of the real value. By default that placeholder is `$MSB_<env_var>`, using the environment variable name exactly as provided, and you can provide a custom placeholder when needed. If the sandbox sends the placeholder to an allowed host, microsandbox swaps it for the real credential at the network boundary. For other destinations, the [violation policy](#violation-policy) controls whether the request is blocked or forwarded with the placeholder unchanged.

That means the guest can call APIs without ever holding the credential itself.

microsandbox checks allowed hosts against the sandbox's observed DNS and TLS identity. Keep allow lists narrow so placeholders can only turn into credentials at the destinations that actually need them.

## Add at create time

Bind secrets to environment variables when you create the sandbox, each scoped to the hosts allowed to receive it:

<CodeGroup>
```typescript TypeScript
import { Sandbox } from "microsandbox";

await using sb = await Sandbox.builder("worker")
    .image("python")
    .secret((s) =>
        s.env("GITHUB_TOKEN")
            .value(process.env.GITHUB_TOKEN!)
            .allowHost("api.github.com")
            .allowHostPattern("*.githubusercontent.com"),
    )
    .secretEnv("SERVICE_API_KEY", process.env.SERVICE_API_KEY!, "api.example.com")
    .create();
```

```rust Rust
use microsandbox::Sandbox;

let sb = Sandbox::builder("worker")
    .image("python")
    .secret(|s| s
        .env("GITHUB_TOKEN")
        .value(std::env::var("GITHUB_TOKEN")?)
        .allow_host("api.github.com")
        .allow_host_pattern("*.githubusercontent.com")
    )
    .secret_env("SERVICE_API_KEY", service_api_key, "api.example.com")
    .create()
    .await?;
```

```python Python
import os
from microsandbox import Sandbox, Secret

sb = await Sandbox.create(
    "worker",
    image="python",
    secrets=[
        Secret.env(
            "GITHUB_TOKEN",
            value=os.environ["GITHUB_TOKEN"],
            allow_hosts=["api.github.com"],
            allow_host_patterns=["*.githubusercontent.com"],
        ),
        Secret.env(
            "SERVICE_API_KEY",
            value=os.environ["SERVICE_API_KEY"],
            allow_hosts=["api.example.com"],
        ),
    ],
)
```

```go Go
sb, err := m.CreateSandbox(ctx, "worker",
    m.WithImage("python"),
    m.WithSecrets(
        m.Secret.Env("GITHUB_TOKEN", os.Getenv("GITHUB_TOKEN"),
            m.SecretEnvOptions{
                AllowHosts:        []string{"api.github.com"},
                AllowHostPatterns: []string{"*.githubusercontent.com"},
            },
        ),
        m.Secret.Env("SERVICE_API_KEY", os.Getenv("SERVICE_API_KEY"),
            m.SecretEnvOptions{AllowHosts: []string{"api.example.com"}},
        ),
    ),
)
```

```bash CLI
msb create python --name worker \
  --secret "GITHUB_TOKEN@api.github.com,*.githubusercontent.com" \
  --secret "SERVICE_API_KEY@api.example.com"
```

</CodeGroup>

In the CLI form, `ENV@HOST[,HOST...]` records a host-side source reference: the real value is read from the same-named host environment variable when the sandbox starts, and never lands in the durable config. The inline `ENV=VALUE@HOST` form is rejected on both `msb create` and `msb modify` (shell history and process listings would leak the value regardless), so providing a raw value is SDK-only.

<Warning>
  **Raw values are saved to disk.** When you pass a raw value through an SDK (`.value(..)`, `secret_env()`, or a value-based rotate), it is stored as-is in the sandbox config file and stays there until you rotate the secret to a reference. The sandbox behaves the same either way; the only difference is what ends up on disk. Prefer references whenever the value is available in a host environment variable.
</Warning>

## Violation policy

A secret's allowed hosts control where its placeholder can become a real credential. When microsandbox detects the placeholder in an inspected request to a destination that is not eligible for substitution, it applies the secret violation policy.

| Action | Behavior |
| ------ | -------- |
| `block-and-log` (default) | Block the request and emit a warning in the host logs. |
| `block` | Block the request without a violation log. |
| `block-and-terminate` | Block the request, log an error, and stop the sandbox. |
| `passthrough` | Forward the placeholder unchanged to matching hosts. This never authorizes credential substitution. |

Set the sandbox-wide policy through networking configuration, or override it for an individual secret. For example, this sandbox stops on violations, but lets a test endpoint receive `API_KEY`'s placeholder unchanged:

```typescript
import { Sandbox } from "microsandbox";

await using sb = await Sandbox.builder("worker")
  .image("python")
  .network((n) => n.onSecretViolation((v) => v.blockAndTerminate()))
  .secret((s) => s
    .env("API_KEY")
    .value(process.env.API_KEY!)
    .allowHost("api.example.com")
    .onViolation((v) => v.passthroughHost("test.example.com")),
  )
  .create();
```

Requests to `api.example.com` can receive the real credential. Requests to `test.example.com` keep the placeholder. Other destinations fall back to the sandbox-wide policy. If the sandbox-wide policy is itself scoped passthrough, destinations outside its host list fall back to `block-and-log`.

For the CLI, set the sandbox-wide action at creation:

```bash
msb create python --name worker \
  --secret "API_KEY@api.example.com" \
  --on-secret-violation block-and-terminate
```

CLI `passthrough` applies to all hosts; use an SDK for host-scoped passthrough. Neither a substitution allow list nor passthrough bypasses the sandbox's network access rules.

See the policy references for [TypeScript](/sdk/typescript/secrets#violationactionbuilder), [Rust](/sdk/rust/secrets#violationaction), [Python](/sdk/python/secrets#violationpolicy), and [Go](/sdk/go/secrets#violationactionstring-enum).

## Where injection works

- **TLS:** By default, substitution requires verified, intercepted TLS. Bypassed TLS is opaque and cannot use secret injection or placeholder inspection. See [TLS inspection](/networking/tls).
- **Headers and Basic auth:** Enabled by default. Use the guest environment variable in the request, for example `Authorization: Bearer <placeholder>`; Basic auth is decoded, substituted, and re-encoded.
- **Query parameters and request bodies:** Disabled by default. Enable them explicitly with the SDK's injection options when the API requires them. Body rewriting has format and encoding limits; see [SecretInjection](/sdk/typescript/secrets#secretinjection).
- **Host patterns:** `*.example.com` includes `example.com` and its subdomains. Prefer exact hosts when only one endpoint needs the credential.

This mechanism does not supply a real credential to guest code that must read it locally, such as code that signs a request itself. Do not replace a secret binding with a plain environment variable to work around an injection issue: that gives the guest the real value. Allowed servers receive the credential and must also be trusted not to return it to the guest. See [Secret handling](/security/secrets) for the security boundary.

## Troubleshooting

| Symptom | Check |
| ------- | ----- |
| A request fails and the sandbox stays running | Look for a secret violation warning in the host logs. Check the destination against the secret's allowed hosts, including any redirect destinations. |
| The sandbox stops after a request | Check whether the effective policy is `block-and-terminate`. |
| The API receives a placeholder or returns an authentication error | Check TLS interception, the destination, and whether the placeholder is in an enabled injection location. A passthrough rule deliberately sends the placeholder unchanged. |
| The guest prints `$MSB_API_KEY` | This is expected. The real credential is injected only at the network boundary. |

## Change while running

<Tooltip tip="modify is not yet available on microsandbox cloud; recreate the sandbox to change its secrets."><span className="msb-badge-local">Local-only <Icon icon="circle-info" size={11} /></span></Tooltip>
Rotate or remove existing secrets without a restart. Adding a secret or changing its guest-visible placeholder requires a restart so the new environment reaches the guest. Later rotations keep that placeholder stable and only change the value injected at the network boundary.

<CodeGroup>
```typescript TypeScript
await sandbox.modify({
  secrets: {
    API_KEY: { env: "API_KEY", allowedHosts: ["api.example.com"] },
  },
  policy: "restart",
});

await sandbox.modify({ secretsRemove: ["SERVICE_API_KEY"] });
```

```rust Rust
let plan = sb.modify()
    .secret(|s| s
        .env("API_KEY")
        .source(SecretSource::Env { var: "API_KEY".into() })
        .allow_host("api.example.com"))
    .restart()
    .apply()
    .await?;
```

```python Python
from microsandbox import ModificationPolicy

await sb.modify(
    secrets={
        "API_KEY": {
            "env": "API_KEY",
            "allowed_hosts": ["api.example.com"],
        },
    },
    policy=ModificationPolicy.RESTART,
)

await sb.modify(secrets_rm=["SERVICE_API_KEY"])
```

```go Go
_, err := sb.Modify(ctx, m.ModifyOptions{
    Secrets: map[string]m.SecretModifySpec{
        "API_KEY": {
            Env:          "API_KEY",
            AllowedHosts: []string{"api.example.com"},
        },
    },
    Policy: m.ModificationPolicyRestart,
})

_, err = sb.Modify(ctx, m.ModifyOptions{
    SecretsRemove: []string{"SERVICE_API_KEY"},
})
```

```bash CLI
msb modify worker --secret GITHUB_TOKEN@api.github.com --restart  # add or rotate
msb modify worker --secret-rm SERVICE_API_KEY                       # remove
```
</CodeGroup>

Secret modification is available through every SDK and the CLI. See [Live Modify](/sandboxes/tuning) for how changes are planned and applied.
