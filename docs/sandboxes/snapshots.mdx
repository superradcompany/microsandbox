<Tooltip tip="Cloud supports stopped or crashed disk snapshots and disk restore. Live capture, full checkpoints, branching, groups, and local artifact archives remain local-only."><span className="msb-badge-limited">Limited on cloud <Icon icon="circle-info" size={11} /></span></Tooltip>

A local snapshot is a portable artifact that can hold either a sandbox's writable disk state or a full checkpoint of a running sandbox. Managed and flat OCI roots are supported; the descriptor preserves the root layout so a flat `rootfs.raw` is never mistaken for a managed OverlayFS upper. Move it with `scp`, archive it as `.msb`, or create a child sandbox from it. Cloud disk snapshots use managed storage or the organization's host volume and support create, get, list, open, remove, and dedicated disk restore. Local-only options are rejected explicitly.

<Note>
Local disk snapshots work with running, paused, stopped, or crashed sandboxes. A running disk capture briefly pauses the VM, seals its disk, and resumes it without copying RAM. Full snapshots use `--full` to include memory and execution state. A user-paused source stays paused in either mode. Cloud disk capture requires a stopped or crashed source.
</Note>

<Note>
Snapshot objects expose a backend-neutral `reference` and reference kind. Pass the snapshot object directly where supported, or pass its typed reference to the dedicated restore API. The local `path` accessor remains available but fails for cloud snapshots, whose storage is not on the client host. A reference preserves addressing; it does not make local-only restore options available on cloud.
</Note>

## What gets captured

`.msb` is the recommended snapshot archive extension; compression defaults to tar + zstd. Archives are recognized by their contents, so existing `.tar.zst`, `.tar`, and other filenames still work. Explicit output filenames are kept as given. Disk-only, full, and incremental exports use the same extension; the archive records what it contains.

| Mode | Source | Captured state | Restore behavior |
| ---- | ------ | -------------- | ---------------- |
| Disk (default) | Running, paused, stopped, or crashed sandbox | Writable disk closure and pinned image | Cold-boots a fresh VM |
| Full | Running or user-paused sandbox | Disk, memory, vCPU, device, and admitted resource state | Resumes the captured execution in a child VM |

Both modes produce the same schema-1 `snapshot.json` descriptor. Its closed `state.kind` is either `file` or `checkpoint`, and `root_disk.layout` records `managed`, `flat`, or `tmpfs`. Checkpoint payloads live in a content-addressed closure rather than a standalone disk file. A tmpfs root has no stopped disk snapshot because its writable state exists only in memory, but it is included in a running full snapshot; such a snapshot must be resumed and cannot use `--disk-only`.

Full restore inherits the captured CPU and memory sizes, including their maximums. Explicit CPU and memory settings in the CLI or SDK restore API must match; conflicting settings are rejected rather than ignored. Disk-only restore boots afresh and can use different resources.

## Share restored memory with CoW

On supported Linux, macOS, and Windows hosts, add `--forked` when restoring a full snapshot to share clean memory pages between children. Writes stay private to each child. Without the flag, restore eagerly copies memory. The source needs no special creation option.

```bash
msb create alpine --name baseline --root-disk flat:1G
msb snapshot create ready --from-sandbox baseline --full
msb restore baseline:ready --name worker-a --forked
msb restore baseline:ready --name worker-b --forked
```

The SDK restore options are Rust `.forked()`, Python `forked=True`, TypeScript `.forked()`, and Go `WithForked()`. The option requires a full snapshot and cannot be combined with `--disk-only` or an image cold boot.

Snapshots are still manual. CoW uses a protected local memory cache; the first uncached restore must build it, while later children reuse it. Captures from forked children can prepare later restore backing with filesystem reflinks when available. Removing the input archive does not invalidate a running child's backing. Explicit NUMA placement with CoW is not supported yet; requests fail instead of silently switching modes.

If a restore fails after creating a child record, remove that child and create a new one from the snapshot. An incomplete restore cannot be started as a fresh VM or modified; the original snapshot remains reusable.

## External mounts

Full snapshots preserve the guest's open-handle state for directory bind mounts, named directory volumes, and isolated single-file binds. Their host filesystem contents remain external dependencies: capturing a snapshot does not copy or freeze later host edits. Restore validates the captured binding and object identities before resuming. Use the existing mount options, keyed by guest path, when the destination needs an explicit replacement binding; a path recorded by another host is not permission to access it. A remapped single-file bind may use a different host basename while keeping the captured guest filename and sibling isolation.

Capture supports tracked objects that can be reopened safely. Guest-renamed objects are preserved when still reopenable, but open-unlinked files and special objects fail capture explicitly; snapshots do not copy host data to make those cases portable. Symlink validation checks link text without reading target files or recursively copying or hashing target contents.

Restore and branch leave host filesystems unmapped unless you supply bindings or explicitly use `--dangerously-inherit-resources`. Unmapped filesystems retain their guest devices but grant no host access; backend operations return `EIO`, with warnings under either policy. This intentional omission does not fail strict validation.

Strict validation is the default for authorized mappings. For example, `msb restore saved --name child -v /host/copy:/work --external-mount-policy relaxed` accepts supported mismatches between the supplied directory and captured state. The SDK equivalents are Rust `.external_mount_policy(ExternalMountRestorePolicy::Relaxed)`, Python `external_mount_policy="relaxed"`, TypeScript `.externalMountPolicy("relaxed")`, and Go `WithExternalMountPolicy(ExternalMountRelaxed)`. Read warnings with Rust/Python `restore_warnings`, TypeScript `restoreWarnings`, or Go `RestoreWarnings`; each identifies the guest path, reason, and stale inode IDs. Stale captured objects fail with `ESTALE` when an operation reaches the filesystem backend. Relaxed mode does not recreate missing files, grant access to unmapped paths, or waive snapshot integrity checks.

Full snapshots also retain clean guest filesystem cache pages. Reads or memory mappings may therefore return previously captured bytes before reaching the backend; relaxed restore does not promise immediate cache invalidation. Capture synchronizes dirty guest writes before admitting external mounts, so the saved cache is not permission to replay stale dirty writes onto a changed destination.

Strict validation checks the mount at restore time; it does not lock the host directory afterward. If source and child map the same host directory, writes reach the same files and host edits can affect both. Cached attributes and file contents can expire separately—even a read's length can be stale. Coordinate shared writes in your application; use managed disk volumes when children need private filesystem state.

Named disk volumes are captured as immutable disk generations. Restored children receive private copies; the source volume is unchanged. Arbitrary external disk-image mounts are not implicitly converted into snapshot-owned volumes.

[Owned volumes](/sandboxes/volumes#owned-volumes) are included automatically in snapshots and branches. Each child gets private directory or disk contents; no host mapping is needed. Full captures also preserve supported open directory-volume handles, including unlinked regular files.

Snapshots containing owned directories cannot move between Unix (macOS/Linux) and Windows: their filesystem metadata is platform-specific. This restriction also applies to disk-only snapshots and archives containing owned directories. Owned disks do not have this directory-format restriction; full restore has its own execution-state compatibility requirements.

## Branch a running sandbox

Use `branch` for an independent local child without first saving a full snapshot:

```bash
msb branch baseline --name worker
```

The child resumes the captured processes, memory, and disk state. Its private memory and managed-disk writes do not affect the source; external mounts remain shared host dependencies unless explicitly remapped. CoW memory is built in—no `--forked` flag is needed. A running source resumes after capture; a user-paused source stays paused. Branches work on supported Linux, macOS, and Windows hosts, require a new child name, and cannot inherit published host ports.

The SDK methods are Rust `source.branch("worker").branch().await?`, Python `await source.branch("worker")`, TypeScript `await source.branch("worker")`, and Go `source.Branch(ctx, "worker")`. They also work on sandbox handles returned by `get`.

For children that should start from the same moment, use `msb branch baseline --names alice bob charlie`. This captures RAM, CPU/device state, and disks once, then starts up to four children concurrently; children share immutable backing and keep their own writes private. The source resumes after capture unless it was already paused. No durable snapshot is created, and deleting the source or one child does not invalidate the others.

SDKs accept a list of names: Rust `source.branch_many(["alice", "bob"]).branch().await?`, Python `await source.branch_many(["alice", "bob"])`, TypeScript `await source.branchMany(["alice", "bob"])`, and Go `source.BranchMany(ctx, []string{"alice", "bob"})`. Validation or capture errors fail the call. Children can become ready in any order, but results follow input order and contain each child's name and either its sandbox or startup error; successful children are retained. Rust exposes that pair as `name` and `result`; Python/TypeScript use `name`, `sandbox`, and `error`; Go uses `Name`, `Sandbox`, and `Error`.

Local branching still writes a consistent memory backing file, but skips portable RAM packaging and snapshot registration. It is not a saved recovery point. Use `snapshot create --full` when you need a durable, exportable snapshot.

On Linux, eligible later branches use anonymous RAM-backed files (`memfd`) instead of named files in `/dev/shm`. Children own their backing independently, and Linux releases it after the last owner exits. Disk backing is retained when RAM is constrained or filesystem reflinks are available. This does not make separate captures share their backing automatically.

You can branch a child again. While its inherited baseline remains valid, it reuses that memory backing and captures the pages changed since restore, without eagerly copying all RAM when the child starts. Preparing the next backing can still require a copy on filesystems without reflink support.

## Quick start

You'll usually reach for the CLI first:

```bash
# 1. Boot a sandbox, install state, then stop it
msb run --name baseline --detach python:3.12
msb exec baseline -- pip install requests
msb stop baseline

# 2. Snapshot the stopped sandbox
msb snapshot create after-pip-install --from-sandbox baseline

# 3. Boot a fresh sandbox from the snapshot
msb restore baseline:after-pip-install --name worker
msb exec worker -- python -c "import requests; print(requests.__version__)"
```

<Tip>
The snapshot belongs to the source's group, `baseline`, and lives at `~/.microsandbox/snapshots/baseline/snap_<id>/`. Its friendly name is `baseline:after-pip-install`.
</Tip>

## Snapshot a sandbox

Each capture is an immutable member of a snapshot group. The group defaults to the source sandbox's name; use `--group` to choose another. Member names are local aliases, while the descriptor carries a stable `snap_...` identity. Omitting the member name generates one. A destination directory selects another group-store root (`DIR/<group>/<snapshot_id>`).

## Groups and head selection

Use a bare group to restore its selected head, or `group:member` for an exact checkpoint:

```bash
msb snapshot create cp01 --from-sandbox baseline --group work
msb snapshot create cp02 --from-sandbox baseline --group work
msb restore work --name latest
msb restore work:cp01 --name earlier

msb snapshot head work           # Show the selected snapshot ID
msb snapshot head work:cp01      # Explicitly select an earlier checkpoint
```

The first snapshot initializes the head. Later captures or imports advance it only when known ancestry proves they descend from the current head. Importing an older checkpoint, a sibling, or one with missing history keeps the head unchanged. Both members remain available. Concurrent siblings use the first successful head update; the other capture still succeeds. There is no special main branch and timestamps do not decide the winner.

```text
work:cp01 ---- work:cp02 ---- work:cp03  <- head
                    \
                     +------ work:experiment
```

`msb snapshot head work:experiment` selects the other branch. Import with `--set-head` to explicitly select the imported archive's head. Missing historical checkpoints are allowed if the snapshot's disk and RAM dependencies are complete. Imports resolve payload dependencies from the supplied archives and an explicitly named destination group; `--base` supplies an external fallback.

```bash
msb snapshot load checkpoint.msb --group work
msb snapshot load experiment.msb --group work --set-head
```

Loading without `--group` creates a fresh generated group. The same archive can be imported into different groups without overwriting either copy. Within a group, an identical ID/descriptor is reusable; conflicting IDs or names fail. A current head cannot be removed while other members remain—select another first. Existing flat snapshot directories can still be opened by explicit path.

An interrupted call may already have published its snapshot. Inspect the group before retrying; member publication never overwrites an existing snapshot.

## Load a set of archives

Import a baseline and its dependent archives together. The shell expands the wildcard; archive order does not matter:

```bash
msb snapshot load checkpoints/*.msb --group received
msb snapshot load changes.msb base.msb --group received --dest /mnt/snapshots
```

`load` accepts one or more archive paths. Use `--dest DIR` for a different group-store root; a trailing positional path is another archive, not a destination. A batch without `--group` creates one generated group for all its archives. Existing single-archive calls still print the digest followed by the installed path. Multi-archive calls print each result and report the batch's head decision once.

Dependencies are resolved from the batch and exact matching snapshots already installed in the explicitly named destination group. For example, after importing `base.msb` into `received`, `msb snapshot load changes.msb --group received` can reuse that base automatically. Use `--base SOURCE` when a dependency must come from another installed snapshot or standalone archive. Imports do not search unrelated groups or nearby archive files. These operations accept the existing archive format; no format conversion or schema bump is required.

All requested members are validated before publication. A batch with one tip follows the normal head-update rules. If a batch contains divergent tips, the existing group head stays selected; a new group has no head until you choose a member with `msb snapshot head GROUP:MEMBER`. `--set-head` requires a unique batch tip and rejects an ambiguous batch before publishing members. The final printed result is not necessarily the selected head.

Use `--output ./saved.msb` (or `-o ./saved.msb`) in either mode to write an archive without installing a snapshot directory.

## Capture a running sandbox

Use full mode when the child must continue the captured processes and memory instead of cold-booting from disk state:

<CodeGroup>
```typescript TypeScript
const snap = await Snapshot.builder("worker-checkpoint")
  .fromSandbox("worker")
  .full()
  .create();
```

```rust Rust
let snap = Snapshot::builder("worker-checkpoint")
    .from_sandbox("worker")
    .full()
    .create()
    .await?;
```

```python Python
snap = await Snapshot.create(
    "worker-checkpoint",
    from_sandbox="worker",
    full=True,
)
```

```go Go
snap, err := m.Snapshot.Create(ctx, m.SnapshotCreateOptions{
    Name:        "worker-checkpoint",
    FromSandbox: "worker",
    Full:   true,
})
```

```bash CLI
msb snapshot create worker-checkpoint --from-sandbox worker --full
```
</CodeGroup>

Capture briefly quiesces the VM, publishes one same-epoch checkpoint, and returns the source to running state. The first capture records a full memory generation; later captures may reuse unchanged objects through retained dirty tracking while every published manifest still describes complete logical memory.

If capture saves the snapshot but cannot recover the source, the command fails and prints the saved artifact's location. The snapshot remains usable; do not automatically retry capture or resume the source. SDKs return a `SnapshotSourceRecoveryError` with the saved artifact details (Rust: `MicrosandboxError::SnapshotSourceRecovery`). If packaging also failed, the error identifies only the retained runtime checkpoint, not a completed snapshot.

Creating a sandbox from the resulting snapshot restores into a child-owned disk generation and installs a fresh VM Generation ID. Before your processes continue, the guest kernel corrects its wall clock and acknowledges activation; the runtime then thaws the workload and publishes network access last. Full restore requires the matching clock-aware kernel. Older development full snapshots must be recaptured, or restored with `--disk-only` where supported. Restore is eager: the archive or installed artifact is no longer needed after construction succeeds.

RAM preparation has no fixed timeout, including the first forked restore on slow storage. SDK creation progress reports this work; `activating` means the VM is constructed and ready to resume, not that it is already usable. Clock synchronization and workload thaw still have bounded waits. You can cancel creation or apply your own overall deadline.

Full restore preserves captured processes, but not the host connections that controlled them. Open a new client connection after restore. Inherited process output is drained without being sent to new clients; host filesystem and TCP transfers must be restarted.

Application TCP connections also depend on host-side proxy state that is not captured. Applications need reconnect/retry handling; a restored socket can wait for its protocol timeout instead of failing immediately. This is separate from reconnecting the SDK or CLI client.

Full restore and branching preserve the virtual gateway's identity so cached ARP/IPv6 neighbour entries still work. Each child gets an independent host network backend, not the source's connections. Older development full snapshots without a captured gateway identity must be recaptured; `--disk-only` does not require it.

## Export changes and compact a disk chain

Repeated disk and full checkpoints add disk layers. You choose when to export changes and when to compact; neither happens automatically.

```bash
msb snapshot create checkpoint-b --from-sandbox worker --full
msb snapshot save worker:checkpoint-b changes.msb --since worker:checkpoint-a
msb modify worker --compact --layers 3 --dry-run
msb modify worker --compact --layers 3
msb modify worker --compact --disk /data --layers 3
msb modify worker --compact --root-disk-only
```

Compaction defaults to the managed or flat root plus every sandbox-owned data disk. Named volumes, external disks, and owned directories are never included. `--disk /data` selects one owned disk by guest mount path; `--disk /` and `--root-disk-only` select only the root. The two selector flags cannot be combined. Explicitly selecting a directory, named/external disk, or absent root fails before compaction.

`--layers 3` merges **up to** the oldest three sealed physical layers per selected disk, **including the base**. It never includes the writable head, even when stopped. The limit must be at least two. Omit `--layers` to merge all sealed layers; a chain with fewer than two sealed layers is unchanged. Compaction is local-only and requires a running or fully stopped sandbox; paused and draining sources are rejected. Results contain aggregate and per-disk counts. With no eligible disks the default selection succeeds with an empty disk list, zero layer and byte counts, and no VM pause. Existing snapshots remain valid and retain their storage until you remove them separately.

Multi-disk compaction is not an all-or-nothing transaction: each disk has its own durable journal. If a disk commit or backend switch fails, the error names the affected disk and any already committed disks; a running VM remains paused for recovery. Do not assume rollback or blindly retry. Restart the sandbox so each disk reopens from its journal. Existing snapshots are unchanged by this recovery.

The aggregate `total_us` covers the whole operation, and `pause_us` measures the shared live VM pause. Each per-disk `total_us` measures preparation and materialization only, excluding journal adoption and backend switching. All timings are microseconds; materialized bytes measure work performed, not reclaimed disk space.

`--since` omits root and owned-disk layers and, for full checkpoints, RAM objects already supplied by the base. The base must be an exact physical prefix for the root and every owned disk present in both snapshots. A newly added owned disk is exported completely. Owned directory namespaces are always complete; unchanged immutable file payloads can be supplied by the base. Each full archive still includes its complete memory map and CPU/device state; it does not replay earlier memory images. Alternatively, `--last-layers 2` selects the newest root-disk layers while retaining complete owned disks and all required RAM objects. Import these smaller archives with their bases in the same batch, into a named group containing their dependencies, or with an explicit external base. Direct restore still accepts an explicit base:

```bash
msb snapshot load changes.msb --base worker:checkpoint-a --group imported
msb restore changes.msb --name child --snapshot-base worker:checkpoint-a
```

An explicit external base can also be a standalone snapshot archive. Dependent archives can supply one another within a batch; they need not be loaded in dependency order. Loads resolve disk and RAM dependencies without starting a VM; only the final sandbox creation resumes execution. Missing or incorrect dependencies fail before publication or execution. Loaded snapshots and restored children own their required files, so removing the base later does not break them. Direct restore skips installing an intermediate snapshot. Add `--disk-only` to cold-boot only disk state. After compacting any root or owned-disk prefix, export a new standalone baseline before using `--since` again: a mismatch in any matched disk refuses the export rather than silently including that disk in full. Do not combine compaction with unrelated `modify` options, or `--since`/`--last-layers` with each other or `--with-parents`/whole-group exports.

Live runtime-sealed disk and full checkpoints preserve reusable sealed ancestry. Independently captured stopped root snapshots may receive new layer identities even when bytes are unchanged, including when recapturing a restored chain. Use a standalone export when such a capture does not match the base's exact physical prefix.

## Capture directly to an archive

When the archive is the desired result, capture straight into it instead of creating an installed snapshot directory and then saving a second copy:

<CodeGroup>
```typescript TypeScript
import { Snapshot } from "microsandbox";

const archive = await Snapshot.builder("after-pip-install")
  .fromSandbox("baseline")
  .createArchive("/tmp/after-pip-install.tar.zst");
```

```rust Rust
use microsandbox::Snapshot;

let archive = Snapshot::builder("after-pip-install")
    .from_sandbox("baseline")
    .create_archive("/tmp/after-pip-install.msb", false)
    .await?;
```

```python Python
from microsandbox import Snapshot

archive = await Snapshot.create_archive(
    "after-pip-install",
    "/tmp/after-pip-install.msb",
    from_sandbox="baseline",
)
```

```go Go
archive, err := m.Snapshot.CreateArchive(ctx, m.SnapshotArchiveOptions{
    SnapshotCreateOptions: m.SnapshotCreateOptions{
        Name:        "after-pip-install",
        FromSandbox: "baseline",
    },
    ArchivePath: "/tmp/after-pip-install.msb",
})
```

```bash CLI
msb snapshot create after-pip-install \
    --from-sandbox baseline \
    -o /tmp/after-pip-install.msb
```
</CodeGroup>

Direct capture publishes only the archive and returns its snapshot ID and path. It creates no intermediate snapshot directory and no local index row. Add `--full` to capture a running sandbox directly to the same archive, or `--plain-tar` to skip zstd compression.

An explicit archive path can also be used directly as the source of a new sandbox:

```bash
msb restore ./after-pip-install.msb --name worker
msb exec worker -- python -V
```

The same archive path works with the SDK restore methods shown below. The archive is unpacked into child-owned staging, so no intermediate installed snapshot is loaded into `~/.microsandbox/snapshots`.

<Note>
Direct capture records the pinned image identity, but does not bundle the cached OCI image. A flat snapshot already contains the complete disk, so restore only needs the pinned image's configuration from cache or the registry; it does not download the original disk layers again. Layered snapshots still need their base image artifacts. For an offline target, create an installed snapshot and use `msb snapshot save --with-image`: it bundles image configuration for flat roots, and the complete base-image cache for layered roots.
</Note>

## Boot from a snapshot

A snapshot already pins its image, so booting from one is mutually exclusive with the image source:

<CodeGroup>
```typescript TypeScript
import { Sandbox } from "microsandbox";

const sb = await Sandbox.restore("baseline:after-pip-install")
    .name("worker")
    .restore();
```

```rust Rust
use microsandbox::Sandbox;

let sb = Sandbox::restore("baseline:after-pip-install")
    .name("worker")
    .restore()
    .await?;
```

```python Python
from microsandbox import Sandbox

sb = await Sandbox.restore("baseline:after-pip-install", name="worker")
```

```go Go
sb, err := m.RestoreSandbox(ctx, "baseline:after-pip-install", "worker")
```

```bash CLI
msb restore baseline:after-pip-install --name worker
msb exec worker -- python -V
```
</CodeGroup>

For disk state, creation cold-boots from a child-owned writable copy. For checkpoint state, creation eagerly restores the captured execution into child-owned state.

A full restore does not also run the image CMD: the captured processes are already the workload. `msb restore` runs the restored sandbox in the background. Run new commands afterward with `msb exec`.

To discard the captured execution and cold-boot only its filesystem state, select disk-only restore:

<CodeGroup>
```typescript TypeScript
const sb = await Sandbox.restore("worker:worker-checkpoint")
  .name("worker")
  .diskOnly()
  .restore();
```

```rust Rust
let sb = Sandbox::restore("worker:worker-checkpoint")
    .name("worker")
    .disk_only()
    .restore()
    .await?;
```

```python Python
sb = await Sandbox.restore("worker:worker-checkpoint", name="worker",
    disk_only=True,
)
```

```go Go
sb, err := m.RestoreSandbox(ctx, "worker:worker-checkpoint", "worker",
    m.WithSnapshotDiskOnly(),
)
```

```bash CLI
msb restore worker:worker-checkpoint --name worker --disk-only
```
</CodeGroup>

Disk-only restore copies only the checkpoint's disk chain, creates a fresh writable qcow2 head, and performs an ordinary boot. It does not require the destination to support the checkpoint's memory or execution codec. Like a live disk snapshot, this disk-only view is crash-consistent: recent writes still buffered in guest RAM may be absent, and filesystem journal recovery may run during boot. Full restore preserves those buffers in captured RAM. Pause and full capture do not automatically sync guest filesystems; host disk flushes and durable snapshot publication are still enforced.

## List, inspect, and remove

<CodeGroup>
```typescript TypeScript
import { Snapshot } from "microsandbox";

const all = await Snapshot.list();                       // Indexed snapshots
const h = await Snapshot.get("baseline:after-pip-install");       // By group/member selector or explicit path
console.log(`${h.name ?? "-"} (${h.digest})`);

await Snapshot.remove("baseline:after-pip-install");
await Snapshot.reindex();                               // Default snapshots directory
```

```rust Rust
use microsandbox::Snapshot;

let all = Snapshot::list().await?; // Indexed snapshots
let h = Snapshot::get("baseline:after-pip-install").await?; // By group/member selector or explicit path
println!("{} ({})", h.name().unwrap_or("-"), h.digest());

Snapshot::remove("baseline:after-pip-install", false).await?;
Snapshot::reindex("/data/snapshots").await?;
```

```python Python
from microsandbox import Snapshot

all = await Snapshot.list()                              # Indexed snapshots
h = await Snapshot.get("baseline:after-pip-install")              # By group/member selector or explicit path
print(f"{h.name or '-'} ({h.digest})")

await Snapshot.remove("baseline:after-pip-install")
await Snapshot.reindex()                                 # Default snapshots directory
```

```go Go
all, err := m.Snapshot.List(ctx)            // Indexed snapshots
fmt.Printf("%d snapshots\n", len(all))
h, err := m.Snapshot.Get(ctx, "baseline:after-pip-install") // By group/member selector or explicit path
name := "-"
if h.Name() != nil {
    name = *h.Name()
}

err = m.Snapshot.Remove(ctx, "baseline:after-pip-install", false)
_, err = m.Snapshot.Reindex(ctx, "/data/snapshots")
```

```bash CLI
msb snapshots                  # Also: msb snaps, msb snapshot ls
msb snapshot inspect baseline:after-pip-install
msb snapshot rm baseline:after-pip-install

# Also if it has indexed children
msb snapshot rm baseline:after-pip-install --force

# Rebuild the index from artifacts on disk
msb snapshot reindex
```
</CodeGroup>

`list` uses a rebuildable local index; group/head selection comes from the artifacts on disk. If the index gets out of sync, `reindex` rebuilds it. Global ID or digest lookup refuses ambiguity when several local copies exist—use a group selector or explicit path. `--force` does not bypass the current-head removal guard.

## Move local snapshots between machines

The snapshot directory is the whole artifact; there is no hidden daemon state. Copy the directory directly, or save it as an archive:

```bash
# Copy the directory directly with scp (image must be cached or pullable on the target)
scp -r ~/.microsandbox/snapshots/baseline/snap_<id> other-host:/tmp/saved-snapshot
# Open that copied artifact by its explicit path; use archive load to add it to a group.

# Bundle into a .msb, transport, then load
msb snapshot save baseline:after-pip-install /tmp/snap.msb
scp /tmp/snap.msb other-host:
ssh other-host msb snapshot load /tmp/snap.msb

# Fully offline: include the OCI image cache so the target needs no network
msb snapshot save baseline:after-pip-install /tmp/snap.msb --with-image
ssh other-host msb snapshot load /tmp/snap.msb
```

Archives use tar + zstd by default; `.msb` is the recommended filename extension. Pass `--plain-tar` for uncompressed tar. SDKs expose the same save and load operations as the CLI.

## Artifact identity and layout

Current file snapshots use a stable opaque snapshot ID, a separate SHA-256 descriptor digest, and one ordered physical layer closure. A normal raw ext4 snapshot is still one layer, whether those bytes represent a managed upper or a complete flat root:

```text
snapshots/
└── baseline/
    ├── group.json                    # selected head ID
    └── snap_<id>/
        ├── snapshot.json             # stable ID + parent ID + disk/state references
        ├── group-member.json         # local name: after-pip-install
        ├── metadata.json             # optional labels
        └── layers/
            └── layer_....raw
```

`metadata.json` contains mutable local labels and does not participate in the descriptor digest or snapshot identity. The descriptor names each layer by `DiskLayerId`. Once a full snapshot has rolled the sandbox onto qcow2, a later disk snapshot carries the complete oldest-first raw/qcow2 chain in this same artifact family; archive save/load and direct archive restore preserve every member.

## Integrity verification

Disk content hashing is optional for disk snapshots, full snapshots and local branches. By default, capture records disk structure and file sizes without scanning the disk for a content hash. Use `--integrity` when you want a persistent disk-content check; already-recorded hashes are retained. Full snapshots still use content-addressed RAM objects. Local branches do not hash RAM.

For example, `msb snapshot create saved --from-sandbox source --full --integrity` records disk integrity alongside the full capture. `msb branch source --name child --integrity` opts in for a local branch. SDKs expose this as `.record_integrity()` in Rust, `record_integrity=True` in Python, `{ recordIntegrity: true }` on TypeScript branches, and `WithBranchIntegrity()` in Go.

Recorded disk integrity uses a fixed 64 KiB-leaf BLAKE3 Merkle tree: known sparse holes collapse into precomputed zero subtrees, while allocated bytes are read and hashed. Verification checks recorded hashes; without them, same-length disk-content corruption cannot be detected by the snapshot layer. File-size, structure and backing-chain checks still apply.

<CodeGroup>
```typescript TypeScript
import { Snapshot } from "microsandbox";

// Compute and record an integrity hash at create time
const snap = await Snapshot.builder("after-pip-install")
  .fromSandbox("baseline")
  .recordIntegrity()
  .create();

// Verify a snapshot's recorded integrity on demand
const report = await snap.verify();
```

```rust Rust
use microsandbox::Snapshot;

// Compute and record an integrity hash at create time
let snap = Snapshot::builder("after-pip-install")
    .from_sandbox("baseline")
    .record_integrity()
    .create()
    .await?;

// Verify a snapshot's recorded integrity on demand

```




</CodeGroup>

`msb snapshot save` and `msb snapshot load` preserve recorded integrity but do not silently execute it. They still enforce the archive grammar, path confinement, entry sizes, descriptor identities, and ordinary archive-entry hashes. Run `msb snapshot verify` explicitly after receiving a snapshot when your workflow requires an independent payload scan. Released `msb-sparse-sha256-v1` descriptors remain readable and verifiable, but ordinary open, boot, save, load, and upgrade paths do not pay their full logical-size SHA cost.

## Use cases

- **Reusable build state.** Install dependencies once, snapshot, then `msb restore ... --name worker` without paying the install cost again. Common pattern for CI, agent workloads, and reproducible dev environments.
- **Portable scratch state.** Capture a sandbox after a long setup, hand the artifact to a teammate or push it to shared storage, and let them boot from the same starting point.
- **Local fork-by-copy.** Multiple sandboxes from one snapshot are independent; each copy of the upper layer diverges on its own.
- **Disaster recovery.** Snapshot a sandbox before a risky migration; if it goes wrong, restore the pre-migration artifact with `msb restore` under a new name.
