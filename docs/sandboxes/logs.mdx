Local sandboxes record captured output to disk so you can read it later, even after the sandbox stops or crashes. Use `msb logs <name>` from the CLI or `logs()` from the SDK. For a running cloud sandbox, use `msb logs -f <name>` or the SDK's live log stream; bounded cloud history is not yet available.

## Read logs

```bash
msb logs devbox
msb logs devbox --tail 100
msb logs devbox -f
msb logs devbox --grep ERROR
msb logs devbox --json | jq 'select(.s == "stderr")'
```

The default output includes user-program `stdout`, `stderr`, and PTY output. Add system diagnostics when you need runtime or kernel logs:

```bash
msb logs devbox --source system
msb logs devbox --source all
```

## What is recorded

`exec.log` records the sandbox's **workload**: the command a detached `msb run` starts, the foreground command of an attached `msb run`, and the SDK's `exec_default` / `attach_default`. Other exec sessions (`msb exec`, an SDK `exec` or `attach`, and interactive shells above all) are **not** recorded unless they ask. A shell's transcript can carry anything typed or printed, and every chunk of it would otherwise be written to the host's disk.

```bash
msb exec devbox --capture -- ./migrate.sh
```

In the SDK, `.capture(true)` on the exec or attach options does the same. To record nothing at all, not even the workload's output, create the sandbox with `--no-exec-log` (`disable_exec_log()` in the SDK, or `sandbox_defaults.disable_exec_log` in `config.json`).

A runtime older than this behaviour records every exec session. Against such a runtime, an explicit `.capture(false)` and `--no-exec-log` fail with an upgrade-required error instead of being silently ignored; an exec that leaves `capture` unset keeps working and is recorded, as it always was there.

## Read from the SDK

<CodeGroup>
```typescript TypeScript
const handle = await Sandbox.get("web");
const entries = await handle.logs();
```

```rust Rust
let handle = Sandbox::get("web").await?;
let entries = handle.logs(&LogOptions::default())?;
```

```python Python
handle = await Sandbox.get("web")
entries = await handle.logs()
```

```go Go
handle, err := m.GetSandbox(ctx, "web")
entries, err := handle.Logs(ctx, m.LogOptions{})
```
</CodeGroup>

Use log options to filter at read time:

<CodeGroup>
```typescript TypeScript
const recent = await handle.logs({
    tail: 50,
    sources: ["stdout", "stderr"],
});
```

```rust Rust
let recent = handle.logs(&LogOptions {
    tail: Some(50),
    sources: vec![LogSource::Stdout, LogSource::Stderr],
    ..Default::default()
})?;
```

```python Python
from microsandbox import LogReadSource

recent = await handle.logs(
    tail=50,
    sources=[LogReadSource.STDOUT, LogReadSource.STDERR],
)
```

```go Go
recent, err := handle.Logs(ctx, m.LogOptions{
    Tail: 50,
    Sources: []m.LogSource{m.LogSourceStdout, m.LogSourceStderr},
})
```
</CodeGroup>

## Sources

| Source | Meaning |
|--------|---------|
| `stdout` | Captured from a recorded non-interactive session's stdout |
| `stderr` | Captured from a recorded non-interactive session's stderr |
| `output` | Captured from a recorded PTY session, where stdout and stderr are merged |
| `system` | Lifecycle markers plus runtime and kernel diagnostics |

Interactive sessions use a PTY, so stdout and stderr are merged before microsandbox receives them. Non-interactive `exec` calls keep the streams separate.

## Diagnostic flows

**Sandbox crashed**

```bash
msb ls
msb logs <name>
msb logs <name> --source system
```

**Sandbox will not start**

```bash
msb create --name nope ...
msb logs nope --source system
```

**Program produced no logs**

`msb create` only boots a sandbox, and an ad-hoc `msb exec` or SDK `exec` is not recorded unless it asks for capture (`--capture`, `.capture(true)`). Run the workload with `msb run`, or pass `--capture`. A sandbox created with `--no-exec-log` records nothing.

## On disk

Sandbox logs live under `<sandbox-dir>/logs/`:

| File | Contents |
|------|----------|
| `exec.log` | The workload's output, and any exec that asked for capture, as JSON Lines |
| `runtime.log` | Sandbox runtime diagnostics |
| `kernel.log` | Guest kernel and agent console output |
| `boot-error.json` | Structured startup failure details, when boot fails early |
