---
title: "SDK contexts and unified resources"
description: "Update existing code for contexts and the unified resource API."
---

Lookups and lists now return `Sandbox`, `Volume`, and `Snapshot` objects you can use directly. Separate Handle types are removed. This is a breaking SDK API change; runtime protocols and persisted resource formats are unchanged.

## Keep default-local workflows simple

Existing local create, get, and list calls still work. They now always run locally; profiles and environment variables no longer switch them to a remote service.

Replace global backend setters and scoped overrides with a `RemoteContext` for remote work, or a `LocalContext` for custom local settings. Objects keep using their original connection. See [remote connections](/cloud/connect#sdk-contexts) for examples.

## Use the returned resource directly

`get` and `list` do not start a stopped sandbox. Commands, file access, and SSH start stopped sandboxes as needed. `ensure_running` explicitly performs that same preparation and returns no new owning object. `get_running` combines lookup and preparation without creating a missing resource.

<CodeGroup>
```typescript TypeScript
import { Sandbox } from "microsandbox";

const sb = await Sandbox.get("worker");
const output = await sb.shell("echo ready");
```

```rust Rust
use microsandbox::Sandbox;

let sb = Sandbox::get("worker").await?;
let output = sb.shell("echo ready").await?;
```

```python Python
from microsandbox import Sandbox

sb = await Sandbox.get("worker")
output = await sb.shell("echo ready")
```

```go Go
sb, err := microsandbox.GetSandbox(ctx, "worker")
if err != nil {
    return err
}
defer sb.Close()
output, err := sb.Shell(ctx, "echo ready")
```

```ruby Ruby
sb = Microsandbox::Sandbox.get("worker")
output = sb.shell("echo ready")
```
</CodeGroup>

Explicit static `start` and `start_detached` are strict: they start an existing stopped resource and fail if it is already running. They do not perform connect-or-start. There is no separate instance `start`; use `ensure_running` only when you need [explicit preparation ahead of work](/sandboxes/lifecycle#prepare-ahead-of-time). Ordinary execution needs no preparation call.

If an object starts a stopped local sandbox, releasing that object and its clones can stop the run. Connecting to an already-running sandbox does not take over its lifetime. Remote sandboxes keep running until explicitly stopped or destroyed. See [lifecycle](/sandboxes/lifecycle) for cleanup and detachment.

## Read current state explicitly

Identity (`id`, `name`, `context`) is synchronous and performs no I/O. A captured name is a lookup label; resource operations target the captured stable identity and must not act on a replacement that reused that name.

Inspection and configuration calls now fetch current backend data. Keep the returned value if you want to reuse that observation without another lookup. For several fields at once, use the information method shown in your [SDK reference](/sdk/overview#reference).

Configuration returns the latest saved settings, which may need a restart to take effect. Volume quota, usage, capacity, and labels are also fetched on demand. Missing measurements remain unknown rather than becoming zero.

Local context `build()` is synchronous and validates configuration immediately; the catalog opens lazily. Profile writers use `kind: "remote"` or `kind: "local"`, while readers still accept `backend` and `cloud`. Older SDKs may reject profiles rewritten in the new format.

## Update cleanup and execution code

Volume and Snapshot instance deletion is `destroy`; static or collection `remove` remains an explicit name/reference-selected convenience. Remote path-based Snapshot destruction reports Unsupported until the provider can atomically enforce the captured identity. Explicit collection removal remains available.

`wait_for_status` signals completion only. Keep using the original resource and call `info` afterward if a new observation is needed. Snapshot `manifest` and `state` load metadata lazily through fallible I/O; get/list do not eagerly read every artifact.

Waiting again returns the command’s recorded result; it does not run the command again or replay output. Cancelling a wait does not mean the command finished.

## Choose the distribution independently

The full packages remain available. Smaller packages install only local or remote support. See [distribution choices](/migrations/sdk-distributions) for installation and runtime requirements.

## Memory values in Python

Memory options accept integer MiB or `Size`, including `Size.gib(1)`. A `Size` value must represent a nonnegative whole number of MiB within the option's integer range; fractional MiB and overflow raise an error before creation or modification. Existing integer inputs keep their MiB meaning.

## Remote connections

Key-only construction connects to managed cloud. Pass an explicit URL to connect to another API; an empty URL now fails.

<CodeGroup>
```typescript TypeScript
const hosted = new RemoteContext({ apiKey });
const other = RemoteContext.withUrl(url, apiKey);
```

```rust Rust
// Previously: RemoteContext::with_api_key(api_key)?
let hosted = RemoteContext::new(api_key)?;
// Previously: RemoteContext::new(url, other_key)?
let other = RemoteContext::with_url(url, other_key)?;
```

```python Python
hosted = RemoteContext(api_key=api_key)
other = RemoteContext.with_url(url, api_key)
```

```go Go
hosted, err := m.NewRemoteContext(apiKey)
if err != nil {
    return err
}
// Previously: m.NewRemoteContext(url, apiKey)
other, err := m.NewRemoteContextWithURL(url, apiKey)
if err != nil {
    return err
}
```

```ruby Ruby
hosted = Microsandbox::RemoteContext.new(api_key: api_key)
other = Microsandbox::RemoteContext.with_url(url, api_key)
```
</CodeGroup>

These are application API changes. Runtime protocols and saved sandbox configuration are unchanged.

## Remote context derivation and authentication

Create a modified copy of a connection to change its URL, API key, or options. Existing objects keep using the original connection. See [connection examples](/cloud/connect#deriving-a-remote-context).

Rust custom HTTP clients now use the context's API key for Authorization, consistently with agent connections. A different default Authorization header on a supplied `reqwest::Client` no longer overrides that key. Pass the intended credential to `RemoteContext` or its derived builder. Custom transport, timeout and user-agent settings retain their existing precedence. Runtime protocols and persisted configuration formats are unchanged.

<Accordion title="Rust client and launch information">
Rust `client()` is now asynchronous and returns an owned `Arc<AgentClient>` bound to the selected local run. Filesystem handles are owned run-bound objects with explicit asynchronous close. Idle filesystem/SSH accessors do not keep a run alive; active operations and open handles retain the run they selected.

### Captured launch outcomes

Rust `sandbox.launch_info()` returns optional `SandboxLaunchInfo` for the sandbox object's retained session. Its `init_owns_boot_workload` and `resumed_from_full_snapshot` flags describe preparation outcomes, not persisted settings or live status. An unprepared lookup returns `None`. The CLI uses these outcomes to avoid executing an init-owned workload twice and to report full-restore warnings. Continue using `config().await?` for current persisted configuration and `status().await?` for current lifecycle state.

</Accordion>
