---
title: "SDK contexts and unified resources"
description: "Migrate destination selection, resource access, inspection and ownership to the redesigned SDK."
---

The redesigned SDK uses one `Sandbox`, `Volume`, and `Snapshot` type each. Lookups and lists return operational resources; there is no separate resource Handle type or conversion step. This is a breaking application API migration. It does not change the runtime protocol or persisted resource format.

## Keep default-local workflows simple

Keep `Sandbox.builder`, `Sandbox::builder`, `Sandbox.create`, and Go's `CreateSandbox` for ordinary local work. The matching get/list and Volume/Snapshot factories remain available. SDK shortcuts always select local execution; environment profiles no longer redirect them.

Replace global backend setters and scoped overrides with an explicit `RemoteContext` or custom `LocalContext`. Builders and returned resources retain that destination. See [context selection](/operations/backends#sdk-contexts) for complete language examples. TypeScript and Python collections are synchronous properties (`context.sandboxes`); Rust and Go use methods (`context.sandboxes()` and `context.Sandboxes()`). Ruby uses ordinary method access. `Sandbox.ctx(context)` and the corresponding Volume/Snapshot entry points remain available.

## Use the returned resource directly

`get` and `list` do not start a stopped sandbox. Execution, filesystem and SSH operations prepare the receiver when needed. `ensure_running` explicitly performs that same preparation and returns no new owning object. `get_running` combines lookup and preparation without creating a missing resource.

<CodeGroup>
```typescript TypeScript
import { Sandbox } from "microsandbox";

const sb = await Sandbox.get("worker");
const output = await sb.shell("echo ready");
```

```rust Rust
use microsandbox::Sandbox;

let sb = Sandbox::get("worker").await?;
let output = sb.shell("echo ready").await?;
```

```python Python
from microsandbox import Sandbox

sb = await Sandbox.get("worker")
output = await sb.shell("echo ready")
```

```go Go
sb, err := microsandbox.GetSandbox(ctx, "worker")
if err != nil { return err }
defer sb.Close()
output, err := sb.Shell(ctx, "echo ready")
```

```ruby Ruby
sb = Microsandbox::Sandbox.get("worker")
output = sb.shell("echo ready")
```
</CodeGroup>

Explicit static `start` and `start_detached` are strict: they start an existing stopped resource and fail if it is already running. They do not perform connect-or-start. There is no separate instance `start`; use `ensure_running` only when you need [explicit preparation ahead of work](/sandboxes/lifecycle#prepare-ahead-of-time). Ordinary execution needs no preparation call.

When preparation starts a stopped local sandbox, the receiving resource retains the new run's ownership. Connecting to an already running sandbox acquires no new shutdown ownership. Remote resources do not gain client-scope shutdown ownership. Use explicit stop or destroy when that is the intended action. See [lifecycle](/sandboxes/lifecycle) for cleanup and detachment.

## Read current state explicitly

Identity (`id`, `name`, `context`) is synchronous and performs no I/O. A captured name is a lookup label; resource operations target the captured stable identity and must not act on a replacement that reused that name.

Mutable inspection and configuration perform fresh backend lookups. Rust `config()` now returns `Result<SandboxConfigInspection>` asynchronously rather than borrowing a captured configuration. TypeScript uses `await sb.config()`, Python uses `await sb.config()`, Go uses `sb.Config(ctx)`, and Ruby's `config` performs the lookup. Keep the returned value yourself when you want an observation without further I/O.

Use `info` to obtain related fields together. `status` and `last_failure_message` are live convenience methods. No refresh call is required, and a failed live lookup does not silently fall back to cached state. Inspection observes one moment; it does not prevent subsequent changes. Configuration means the latest persisted settings, which may require restart before they apply to a running VM.

Volume quota, usage, capacity, and labels also require live inspection: `await volume.info()` in TypeScript/Python, `volume.info().await?` in Rust, `volume.Info(ctx)` in Go, and `volume.info` in Ruby. A missing provider measurement remains unknown rather than becoming zero.

Local context `build()` is synchronous and validates configuration immediately; the catalog opens lazily. Profile writers use `kind: "remote"` or `kind: "local"`, while readers still accept `backend` and `cloud`. Older SDKs may reject profiles rewritten in the new format.

## Update cleanup and execution code

Volume and Snapshot instance deletion is `destroy`; static or collection `remove` remains an explicit name/reference-selected convenience. Remote path-based Snapshot destruction reports Unsupported until the provider can atomically enforce the captured identity. Explicit collection removal remains available.

`wait_for_status` signals completion only. Keep using the original resource and call `info` afterward if a new observation is needed. Snapshot `manifest` and `state` load metadata lazily through fallible I/O; get/list do not eagerly read every artifact.

Execution retains its terminal outcome. A later wait returns the same recorded completion after an earlier wait, collection, or terminal event read. This does not rerun the command or replay its output. Cancelling a caller's wait is not proof that the command finished.

Rust `client()` is now asynchronous and returns an owned `Arc<AgentClient>` bound to the selected local run. Filesystem handles are owned run-bound objects with explicit asynchronous close. Idle filesystem/SSH accessors do not keep a run alive; active operations and open handles retain the run they selected.

## Choose the distribution independently

Full packages remain available. Lean local and remote packages use the same public resource types with a selected native implementation. They exclude runtime executables and firmware. Go's thin modules additionally require explicit FFI provisioning. See [installation](/sdk/overview#select-a-smaller-distribution) for package names and setup; changing the package does not change resource ownership or destination retention.

## Memory values in Python

Memory options accept integer MiB or `Size`, including `Size.gib(1)`. A `Size` value must represent a nonnegative whole number of MiB within the option's integer range; fractional MiB and overflow raise an error before creation or modification. Existing integer inputs keep their MiB meaning.

### Captured launch outcomes

Rust `sandbox.launch_info()` returns optional `SandboxLaunchInfo` for the receiver's retained session. Its `init_owns_boot_workload` and `resumed_from_full_snapshot` flags describe preparation outcomes, not persisted settings or live status. An unprepared lookup returns `None`. The CLI uses these outcomes to avoid executing an init-owned workload twice and to report full-restore warnings. Continue using `config().await?` for current persisted configuration and `status().await?` for current lifecycle state.

## Remote context construction

Key-only constructors now honor `MSB_API_URL`. To pin an endpoint, pass its URL explicitly. In Rust, replace `new(url, key)` with `with_url(url, key)` and `with_api_key(key)` with `new(key)`. In Go, use `NewRemoteContextWithURL(url, key)` for the two-argument form.

TypeScript keeps `new RemoteContext({ apiKey })` and adds `RemoteContext.withUrl(url, apiKey, options?)`. Python keeps `RemoteContext(api_key=...)` and adds `RemoteContext.with_url(url, api_key, ...)`. Ruby keeps `RemoteContext.new(api_key: ...)` and adds `RemoteContext.with_url(url, api_key, ...)`. Existing URL options/keywords remain supported. Builders, explicit environment loading and named profiles retain their roles. See [remote endpoints](/cloud/connect#another-endpoint).

This is a public source API change. Runtime protocols, stored configuration, resource identity and default-local routing are unchanged.

## Remote context derivation and authentication

Use Rust `to_builder()` or TypeScript `toBuilder()` to derive through the existing fluent builder. Python uses `replace(...)`, Ruby uses `with(...)`, and Go uses `WithOptions(...)`; these SDKs do not gain context builders. Derivation preserves captured configuration and native-provider ownership. Existing resources keep their original credentials and endpoint. See [the language examples](/cloud/connect#more-options).

Rust custom HTTP clients now use the context's API key for Authorization, consistently with agent connections. A different default Authorization header on a supplied `reqwest::Client` no longer overrides that key. Pass the intended credential to `RemoteContext` or its derived builder. Custom transport, timeout and user-agent settings retain their existing precedence. Runtime protocols and persisted configuration formats are unchanged.

## Resource selectors and state accessors

Explicit resource-type `local()` / `remote()` selectors return the existing plural collections before builder/create/get/list. Go uses `SandboxLocal()` / `SandboxRemote()` and corresponding Volume/Snapshot functions. Remote selection reads environment credentials; direct resource entry points remain default-local. See [usage and feature availability](/cloud/connect#resource-selectors).

Rust's previous instance `.local()` and `.cloud()` state accessors are now `.local_state()` and `.remote_state()`. Public `SandboxCloudState` and `VolumeCloudState` become `SandboxRemoteState` and `VolumeRemoteState`. This source-breaking rename frees the resource-type selector names. State access remains synchronous and does not replace live inspection. Runtime protocols and persisted field spellings are unchanged.

CLI `--local` / `--remote` override ordinary and managed active-profile selection but still enforce `allowed_backends`. Remote flags use environment credentials; omit them for named-profile credential resolution. `MSB_BACKEND=remote` is accepted alongside legacy `cloud`. Diagnostic JSON uses `remote` for the remote kind. Explicit flag-selected contexts use the existing `programmatic` source value. See [CLI precedence](/cloud/connect#precedence).

## Configuration result shape

`config()` returns a dedicated inspection result rather than creation input. This intentionally changes the public Rust and Go return types and the serialized shape used by TypeScript, Python and Ruby. The result always performs a fresh backend lookup; retaining it gives a snapshot, not a live object. A persisted value is not proof that it has been applied to the running VM.

The serialized envelope has `kind` (`local` or `remote`), `name`, `spec`, `unavailable` and `redacted`. Local `spec` is the persisted task specification, excluding process-local creation options. Remote `spec` is the provider's allowlisted view: OCI reference (or null for an unavailable non-OCI source), resource sizes, runtime settings, environment, labels, resource limits, lifecycle, mount presentation and redacted network metadata. Remote mounts do not expose source identities, and secret descriptors do not contain values or vault paths. Omitted init, security-profile, patches and other unreported fields remain unavailable, never silently defaulted.

Rust uses `inspection.runtime()` and pattern matching on `inspection.settings`, or `local_spec()`/`remote_spec()`. TypeScript reads `inspection.spec.runtime.shell`; Python and Ruby read `inspection["spec"]["runtime"]["shell"]`. Go reads `inspection.Spec.Runtime.Shell` (a pointer, nil when unset). TypeScript camel-cases object keys; the strings in `unavailable` and `redacted` remain snake_case wire paths in every SDK. Use `Kind`/`kind` before interpreting backend-specific source and resource fields.

Do not feed the result back into a creation builder. Keep creation input separately if your application needs to reproduce a task; a redacted inspection response cannot supply withheld source references or credentials. Fetching an existing resource preserves its returned runtime settings for shell and default-command execution without an explicit `ensure_running` call.


## Typed resource and job values

- **Rust** — Match `snapshot.state_kind()` against `SnapshotStateKind::File` or `Checkpoint`. Use `.as_str()` when forwarding the tag, including an unknown indexed value.
- **TypeScript** — `volume.kind` and `(await volume.info()).kind` both return `"dir" | "disk"`. Narrow dynamic pull policies, log levels and job output filters before passing them to the SDK. Fluent configuration callbacks return the configured builder.
- **Python** — `(await sb.info())["status"]` returns a `SandboxStatus`, `context.kind` a `ContextKind`, and `(await volume.info())["kind"]` a `VolumeKind`. Job event tags narrow the payload to output, a replay gap or completed job information. Use `JobState.RUNNING` to compare job state.
- **Go** — Use `JobStateRunning` for job state and `[]JobOutputSource{JobOutputStdout, JobOutputStderr}` for log filters. Progress phases, modification dispositions and live resize outcomes also have named string types. Use `string(value)` when passing one to a function requiring a string.
- **Ruby** — Change `sb.status == "running"` to `sb.status == :running`, including comparisons against `sb.info.fetch("status")`. Context and volume kinds, snapshot kind accessors, job/event tags and log sources return symbols. Use `job.info` for live metadata. Ruby's `job.inspect` formats the object locally.
